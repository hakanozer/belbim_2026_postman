7.1Pre-request ile dinamik veri ve izleme başlığı

Bu konu nedir?

Pre-request script, istek gönderilmeden hemen önce çalışır; istek içeriğini koşu anında hazırlar. Postman'ın dinamik değişkenleri ({{$guid}}, {{$timestamp}}, {{$randomInt}} …) anlık değer üretir; script içinde pm.variables.replaceIn("{{$guid}}") ile alınır.

Neden önemlidir?

Sabit test verisi ikinci koşuda çakışır (aynı e-posta, aynı sipariş numarası) ve izlenemez. Dinamik veri tekrarlanabilirliği artırırken, izleme başlığı (correlation id) test isteğini sunucu loglarında bulmanızı sağlar.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Dağıtık / mikroservis mimarileriBir test isteğini gateway → servis → veritabanı loglarında izlemek için X-Correlation-Id kullanılır.
  • Kayıt / başvuru servisleriTekil e-posta, TCKN benzeri alanlar için her koşuda yeni yapay değer gerekir (Idempotency / unique kısıtı).
  • Tarih içeren iş kurallarıVade, geçerlilik, randevu tarihleri koşu anına göre hesaplanır.

Hangi durumlarda?

  • Her koşuda farklı olması gereken veri için.
  • Üretimdeki bir hatayı log korelasyonuyla bulmak için.
  • Zaman bağımlı kurallar test edilirken.
Uygulamaya hazırlık
  • Collection düzeyi script (izleme başlığı): her isteğe uygulanır.
  • Dinamik veri denemesini yazma yan etkisi olmayan Postman Echo üzerinde yapacağız (POST https://postman-echo.com/post gövdeyi yansıtır).
  • JSONBulut uçlarına yazma isteği göndermiyoruz.
Kod örneği
JavaScriptCollection → Pre-request — izleme başlıkları
// COLLECTION → Scripts → Pre-request
// Her isteğe izleme kimliği ve koşu kimliği ekler.
const runId = pm.collectionVariables.get("runId") || pm.variables.replaceIn("{{$guid}}");
pm.collectionVariables.set("runId", runId);

pm.request.headers.upsert({ key: "X-Correlation-Id", value: pm.variables.replaceIn("{{$guid}}") });
pm.request.headers.upsert({ key: "X-Test-Run-Id", value: runId });
console.log("Correlation:", pm.request.headers.get("X-Correlation-Id"), "| Run:", runId);
JavaScriptPre-request — dinamik yapay veri
// REQUEST (POST https://postman-echo.com/post) → Scripts → Pre-request
// Her koşuda farklı, açıkça YAPAY test verisi üretir.
const stamp = new Date().toISOString().replace(/[-:.TZ]/g, "").slice(0, 14);   // örn. 20261029103015
const suffix = pm.variables.replaceIn("{{$randomInt}}");
pm.variables.set("syntheticEmail", "egitim." + stamp + "." + suffix + "@example.com");
pm.variables.set("syntheticTitle", "Test gonderisi " + stamp);
console.log("Üretilen yapay veri:", pm.variables.get("syntheticEmail"));
JSONAynı isteğin Body → raw → JSON alanı
{
  "email": "{{syntheticEmail}}",
  "title": "{{syntheticTitle}}"
}
JavaScriptPost-response — dinamik veri doğrulaması
// Aynı isteğin Scripts → Post-response sekmesi
pm.test("Dinamik veri Echo yanıtında geri geldi", function () {
  const sent = pm.response.json().json;
  pm.expect(sent.email).to.match(/^egitim\.\d{14}\.\d+@example\.com$/);
  pm.expect(sent.title).to.include("Test gonderisi");
});

pm.test("İzleme başlıkları gönderildi", function () {
  const headers = pm.response.json().headers;
  pm.expect(headers["x-correlation-id"]).to.match(/^[0-9a-f-]{36}$/);
  pm.expect(headers["x-test-run-id"]).to.be.a("string").that.is.not.empty;
});
Kodun açıklaması
  • pm.variables.replaceIn("{{$guid}}") — dinamik değişkeni script içinde değere çevirir ({{$guid}} yalnızca metin alanlarında otomatik çözülür).
  • pm.request.headers.upsert({...}) — header yoksa ekler, varsa günceller; collection düzeyinde çalıştığı için her isteğe uygulanır.
  • runId collection değişkeni, aynı koşudaki tüm istekler için tek bir kimlik sağlar (koşu başına bir kez üretilir).
  • Yapay e-posta example.com alan adını kullanır: bu alan adı belgelendirme için ayrılmıştır, gerçek bir kullanıcıya gitmez.
  • Body'deki {{syntheticEmail}} değişkeni, aynı istekteki Pre-request scriptinin pm.variables.set ile (local) yazdığı değerden çözülür.
Postman'da uygulama
  1. Collection'a tıklayın → Scripts → Pre-request → ilk kodu yapıştırın → Save.
  2. Yeni istek: POST https://postman-echo.com/post. Body → raw → JSON'a üçüncü kod bloğunu yazın.
  3. Aynı isteğin Pre-request sekmesine ikinci, Post-response sekmesine dördüncü kodu yapıştırın; Save ve Send.
  4. Console'da üretilen yapay e-postayı ve izleme kimliğini görün; Test Results'ta iki testin geçtiğini doğrulayın.
  5. İsteği ikinci kez gönderin: e-posta ve correlation id'nin değiştiğini görün.

7.2Tarih, sayı ve metin alanlarını doğrulama

Bu konu nedir?

Alan doğrulaması üç ayrı akıl yürütme gerektirir: tarih (biçim ve anlam: geçmiş/gelecek, saat dilimi), sayı (tip, aralık, tam sayı mı?), metin (boş değil, kırpılmış, beklenen biçim). JSONBulut yanıtlarında tarih alanı yok; bu yüzden tarih mantığını gerçekten bulunan **Date yanıt başlığında** uyguluyoruz.

Neden önemlidir?

“Alan var” testi yetmez: price: -5, stock: 1.5, title: " " hepsi “alan var” testinden geçer. Alan kuralları sözleşmenin iş anlamıdır.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Finans / sigortaTutar, oran, tarih aralığı kuralları (prim, vade, faiz) hata durumunda doğrudan para etkisi yaratır.
  • E-ticaretFiyat > 0, indirim 0–100, stok tam sayı ≥ 0 kuralları katalog kalitesini belirler.
  • Dağıtık sistemlerSaat kayması (clock skew) token ve imza doğrulamalarını bozabilir; yanıt başlığındaki zamanla yerel saati kıyaslamak ilk teşhistir.

Hangi durumlarda?

  • Hesaplanan veya sınırlı alanlar olduğunda.
  • Sözleşmede tip var ama aralık belirtilmemişse (ekip kuralı eklenir).
  • Sunucu ve test makinesi saat uyumu şüphesinde.
Uygulamaya hazırlık
  • İstek: GET https://jsonbulut.com/api/products/1 (kimliksiz).
  • Gözlenen değerler: price 9.99, discountPercentage 7.17, rating 4.94, stock 5.
  • Aralıklar sözleşmede yoktur: 0–100 indirim ve 0–5 puan kuralları ekip varsayımıdır; kendi iş kuralınıza göre değiştirin.
Kod örneği
JavaScriptPost-response — tarih (Date başlığı) kontrolü
pm.test("Sunucu saati yerel saatle ±5 dakika uyumlu (Date header)", function () {
  const serverTime = new Date(pm.response.headers.get("Date")).getTime();
  pm.expect(Number.isNaN(serverTime), "Date ayrıştırılamadı").to.be.false;
  pm.expect(Math.abs(Date.now() - serverTime)).to.be.below(5 * 60 * 1000);
});
JavaScriptPost-response — sayı ve metin kuralları (GET /api/products/1)
pm.test("Sayısal alanlar iş kuralına uygun (ekip kuralı)", function () {
  const product = pm.response.json().data;
  pm.expect(product.price, "price").to.be.a("number").and.to.be.above(0);
  pm.expect(product.discountPercentage, "discountPercentage").to.be.within(0, 100);
  pm.expect(product.rating, "rating").to.be.within(0, 5);
  pm.expect(Number.isInteger(product.stock), "stock tam sayı").to.be.true;
  pm.expect(product.stock, "stock").to.be.at.least(0);
});

pm.test("Metin alanları dolu ve kırpılmış", function () {
  const product = pm.response.json().data;
  ["title", "category", "sku"].forEach(function (key) {
    pm.expect(product[key], key).to.be.a("string");
    pm.expect(product[key].trim(), key + " boş olmamalı").to.not.equal("");
    pm.expect(product[key], key + " baş/son boşluk içermemeli").to.equal(product[key].trim());
  });
  pm.expect(product.images.every(function (u) { return /^https?:\/\//.test(u); }), "images URL biçimi").to.be.true;
});
Kodun açıklaması
  • new Date(headerText).getTime() — HTTP Date başlığını milisaniyeye çevirir; ayrıştırılamazsa NaN olur, bu yüzden önce Number.isNaN ile kontrol ederiz.
  • within(0, 100) — kapalı aralık; above(0) — kesin büyük; at.least(0) — büyük eşit.
  • Number.isInteger(stock) — ondalıklı stok değerini yakalar.
  • product[key].trim() karşılaştırması baş/son boşluk hatalarını yakalar; veri temizliği hataları çoğu zaman buradan çıkar.
  • brand alanını bilerek doğrulamadık: bazı ürünlerde bulunmayabilir ve sözleşmede zorunlu değildir.
Beklenen sonuç

Üç test de geçer. Date başlığı gözlemi: Thu, 29 Oct 2026 07:58:37 GMT biçimi (HTTP-date).

Hata durumları ve çözümleri
BelirtiNedenÇözüm
Saat testi kırmızıMakine saati/saat dilimi yanlış veya VPN gecikmesi.Sistem saatini senkronize edin; kural ±5 dk yerine ekip eşiğiyle değiştirilebilir.

7.3Yanıttan veri alıp sonraki istekte kullanma: zincirleme testler

Bu konu nedir?

Zincirleme test, bir isteğin yanıtından gerçek bir değeri alıp (ör. ilk gönderinin id'si) bir sonraki isteğin URL'sinde kullanmaktır. Değer, collection değişkeni aracılığıyla taşınır: pm.collectionVariables.set (yaz) ve {{postId}} / pm.collectionVariables.get (oku).

Neden önemlidir?

Sabit ID'ler (örn. /api/posts/1) veri değiştiğinde testi kırar. Değeri yanıttan almak, testi veriden bağımsız kılar ve gerçek kullanıcı akışına yaklaştırır.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • E-ticaretSepet oluştur → cartId al → ürün ekle → siparişi onayla zinciri.
  • Bankacılık / sigortaBaşvuru oluştur → applicationId al → durum sorgula → belge ekle.
  • Her listeleme + detay ekranıListe → detay → ilişkili kayıtlar: JSONBulut'taki posts → post → comments zinciri aynı desendir.

Hangi durumlarda?

  • Bir sonraki istek öncekinin ürettiği kimliğe ihtiyaç duyduğunda.
  • Sabit ID'lerin kırılganlığı fark edildiğinde.
  • Uçtan uca akış testi kurulurken.
Uygulamaya hazırlık
  • Collection değişkeni pageSize = 2 (Ders 6). Klasör: 01-Posts-Zincir.
  • Üç istek, bu sırayla: ① GET {{baseUrl}}/api/posts?page=1&per_page={{pageSize}} ② GET {{baseUrl}}/api/posts/{{postId}} ③ GET {{baseUrl}}/api/posts/{{postId}}/comments.
  • postId ilk çalıştırmadan önce boş olacaktır; ① onu dolduracaktır.
Kod örneği
JavaScript① Liste isteği — Post-response
// ① GET /api/posts?page=1&per_page={{pageSize}}  → Scripts → Post-response
const body = pm.response.json();

pm.test("Liste en az bir gönderi içeriyor", function () {
  pm.expect(pm.response.code).to.equal(200);
  pm.expect(body.data).to.be.an("array").that.is.not.empty;
});

if (Array.isArray(body.data) && body.data.length > 0) {
  pm.collectionVariables.set("postId", String(body.data[0].id));
  console.log("postId =", pm.collectionVariables.get("postId"));
}
JavaScript② Detay isteği — Post-response
// ② GET /api/posts/{{postId}}  → Scripts → Post-response
const body = pm.response.json();

pm.test("Detay, seçilen gönderiyi döndürdü", function () {
  pm.expect(pm.response.code).to.equal(200);
  pm.expect(body.data.id).to.equal(Number(pm.collectionVariables.get("postId")));
  pm.expect(body.data.title).to.be.a("string").that.is.not.empty;
});
JavaScript③ Yorum isteği — Post-response
// ③ GET /api/posts/{{postId}}/comments  → Scripts → Post-response
const body = pm.response.json();

pm.test("Tüm yorumlar seçilen gönderiye ait", function () {
  pm.expect(pm.response.code).to.equal(200);
  pm.expect(body.data).to.be.an("array");
  const postId = Number(pm.collectionVariables.get("postId"));
  body.data.forEach(function (comment) {
    pm.expect(comment.post_id, "post_id").to.equal(postId);
  });
});
Kodun açıklaması
  • ① içinde String(body.data[0].id) — değişkenler metin saklandığı için dönüşümü bilerek yapıyoruz.
  • ② içinde Number(...) — metin olarak saklanan değeri, yanıttaki sayı id ile kıyaslamak için sayıya geri çeviriyoruz.
  • ③ forEach — listedeki her yorumun post_id'sini doğrular (yalnızca ilkini değil).
  • Guard (if (Array.isArray…)): liste boşsa postId yazılmaz; sonraki istek bunu fark edip atlayabilir (sonraki konu).
Postman'da uygulama
  1. 01-Posts-Zincir klasörünü oluşturun ve üç isteği bu sırayla içine koyun (URL'lerde {{baseUrl}} ve {{postId}} kullanın).
  2. Her isteğin Scripts → Post-response sekmesine kendi kodunu yapıştırın; Save.
  3. İlk isteği tek başına gönderin; Console'da postId = 1 satırını ve collection Variables sekmesinde postId değerini görün.
  4. İkinci ve üçüncü isteği sırayla gönderin; Test Results'ta testlerin geçtiğini doğrulayın.
  5. Klasörün Run ekranı ile üçünü birlikte çalıştırmayı Ders 9'da yapacağız; şimdilik elle sırayla gönderin.

7.4Akış yönetimi: pm.execution.setNextRequest ve skipRequest

Bu konu nedir?

Collection Runner/CLI isteklerini varsayılan olarak sırayla çalıştırır. **pm.execution.setNextRequest("İstek Adı")** bir sonraki isteği belirler (null verirseniz koşu durur); **pm.execution.skipRequest() Pre-request scriptinde bu isteği göndermeden atlar. Bunlar yalnızca toplu koşuda** (Runner, Postman CLI, Newman) etkilidir; tek istek gönderirken etkisizdir.

Eski ad – yeni ad

Eski eğitimlerdeki postman.setNextRequest() eski (legacy) çağrıdır; güncel karşılığı pm.execution.setNextRequest()'tir. Yeni kodda yalnızca pm.execution.* kullanın. Mümkünse isteği adı yerine kimliğiyle (pm.info.requestId) belirtin: ad değişebilir, kimlik değişmez.

Neden önemlidir?

Zincirin ilk halkası başarısız olduğunda ikinci ve üçüncü isteğin anlamsız hatalarla düşmesini önlemek, kırmızı raporu kök nedene odaklar: tek bir gerçek hata, üç gürültülü hataya dönüşmez.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Uçtan uca iş akışlarıGiriş başarısızsa sonraki adımların hiçbiri çalıştırılmaz; rapor “giriş çalışmadı” der.
  • Ortama bağlı koşullu testlerProduction'da yazma adımları atlanır, yalnızca okuma adımları koşar.

Hangi durumlarda?

  • Bağımlı bir zincirin ilk halkası başarısız olabiliyorsa.
  • Koşula bağlı adım gerekiyorsa.
  • Beklenen bir ön durum yoksa isteği atlamak istenirse.
Kod örneği
JavaScript① Post-response — liste boşsa koşuyu durdur
// ① GET /api/posts  → Scripts → Post-response  (Konu 7.3'teki kodun akış kontrollü hâli)
const body = pm.response.json();

if (!Array.isArray(body.data) || body.data.length === 0) {
  console.warn("Liste boş: zincirin geri kalanı çalıştırılmayacak.");
  pm.execution.setNextRequest(null);   // koşuyu durdurur
} else {
  pm.collectionVariables.set("postId", String(body.data[0].id));
}
JavaScript② ve ③ Pre-request — postId yoksa atla
// ② ve ③ → Scripts → Pre-request: bağımlı değişken yoksa isteği ATLA
if (!pm.collectionVariables.get("postId")) {
  console.warn("postId yok: '" + pm.info.requestName + "' isteği atlandı.");
  pm.execution.skipRequest();
}
Kodun açıklaması
  • setNextRequest(null) — koşuyu mevcut istekten sonra sonlandırır (klasör koşusunda yalnızca o klasörün kapsamı etkilenir).
  • skipRequest() — isteği göndermeden atlar; sonraki isteğe geçilir. Atlanan istek raporda “çalışmadı” görünür.
  • pm.info.requestName — şu anki isteğin adı; pm.info.requestId — kimliği.
  • setNextRequest fonksiyonu mevcut isteğin sonunda uygulanır; ondan sonra yazılan kod da yine çalışır.
Postman'da uygulama
  1. Konu 7.3'teki ① scriptini yukarıdaki sürümle değiştirin; ② ve ③'ün Pre-request sekmesine ikinci kodu yapıştırın.
  2. Collection'daki postId değerini silin (Variables sekmesinde boş bırakın) ve klasörü ② ve ③ ile yalnızca bu iki isteği çalıştıracak biçimde Runner'da (Ders 9) çalıştırın: iki istek de atlanmalı.
  3. Normal koşuda üç istek de çalışır.

Yapın

  • Döngü kuruyorsanız mutlaka çıkış koşulu koyun.
Yapmayın
  • pm.execution.setNextRequest çağrısını tek bir isteği gönderirken sonuç beklemek için kullanmayın (etkisizdir).
  • postman.setNextRequest (eski) çağrısını yeni koda yazmayın.
Beklenen sonuç

postId boşken ② ve ③ gönderilmez, Console'da “atlandı” uyarısı görünür; koşu özetinde bu istekler çalışmamış olarak yer alır.

7.5Veri odaklı test: CSV ve JSON veri dosyaları

Bu konu nedir?

Veri odaklı test (data-driven testing), aynı istek ve aynı test kodunu bir veri dosyasındaki her satır için ayrı bir iterasyonda çalıştırır. CSV'de sütun başlıkları, JSON'da nesne anahtarları değişken adı olur. Scriptte pm.iterationData.get("ad") ile, istekte {{ad}} ile okunur.

Neden önemlidir?

Bir senaryoyu 50 girdiyle çalıştırmak için 50 kopya istek yazmak sürdürülemez. Veri dosyası, test mantığını ve test verisini ayırır: iş analisti yeni bir satır ekleyerek test kapsamını büyütebilir.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Bankacılık / sigortaFaiz, prim, komisyon hesaplayan servislere yüzlerce senaryo satırı verilir (tutar, vade, profil).
  • E-ticaretÜrün arama, filtre ve sıralama kombinasyonları satır satır doğrulanır.
  • Sınır değer / negatif test matrisiHer satır bir sınır değer ve beklenen durum kodudur (expectedStatus).

Hangi durumlarda?

  • Aynı kuralı çok sayıda girdiyle sınadığınızda.
  • Test verisini test ekibi dışındaki kişilerin sürdürmesi gerektiğinde.
  • Regresyonda farklı girdi kombinasyonlarını çalıştırırken.
Uygulamaya hazırlık
  • Salt okunur iki senaryo: sayfalama (CSV) ve ürün araması (JSON). Hepsi GET'tir.
  • Kodlama: dosyaları UTF-8 olarak kaydedin; CSV'de ilk satır başlıktır; JSON'da kök bir dizi olmalıdır.
  • Runner'da özel veri dosyası Postman'ın ücretli planlarında sunulur (v12 yardımı). Planınızda yoksa aynı dosyaları Postman CLI'nın -d seçeneğiyle çalıştırabilirsiniz (Ders 9).
Postman'da uygulama
  1. Bir metin editörü açın (Not Defteri, VS Code, TextEdit düz metin modunda) ve aşağıdaki **posts-pages.csv** içeriğini aynen yazın. Dosyayı posts-pages.csv adıyla, UTF-8 olarak kaydedin.
  2. Başka bir dosyada **products-search.json** içeriğini yazıp kaydedin.
  3. GET Posts - sayfalama (veri odaklı) isteğini oluşturun: URL {{baseUrl}}/api/posts?page={{page}}&per_page={{per_page}}. (Params tablosunda page değeri {{page}}, per_page değeri {{per_page}}.)
  4. İsteğin Post-response sekmesine ilk veri odaklı kodu yapıştırın.
  5. Aynı mantıkla GET Products - arama (veri odaklı) isteğini oluşturun: URL {{baseUrl}}/api/products/search?query={{query}}&per_page=2; ikinci kodu Post-response'a yapıştırın.
  6. Kenar çubuğunda isteklerinizin bulunduğu klasörü (örn. 05-Veri-Odakli) seçin ve Run'a tıklayın. Run type olarak Functional → Local seçin.
  7. Iteration data açılır listesini açın → Datafiles sekmesi → Select from computer ile posts-pages.csv dosyasını seçin; önizlemede 5 satır görün. Iterations değerinin dosyadaki satır sayısına (5) eşit olduğunu doğrulayın.

Yapın

Kod örneği
JavaScriptPost-response — sayfalama (CSV)
// GET {{baseUrl}}/api/posts?page={{page}}&per_page={{per_page}}  → Scripts → Post-response
const body = pm.response.json();
const page = Number(pm.iterationData.get("page"));
const perPage = Number(pm.iterationData.get("per_page"));
const expectedCount = Number(pm.iterationData.get("expectedCount"));

pm.test("Satır " + (pm.info.iteration + 1) + ": page=" + page + ", per_page=" + perPage, function () {
  pm.expect(pm.response.code).to.equal(200);
  pm.expect(body.meta.pagination.page).to.equal(page);
  pm.expect(body.meta.pagination.per_page).to.equal(perPage);
  pm.expect(body.data.length).to.equal(expectedCount);
});
JavaScriptPost-response — ürün arama (JSON, beklenen durum veri dosyasında)
// GET {{baseUrl}}/api/products/search?query={{query}}&per_page=2  → Scripts → Post-response
const expectedStatus = Number(pm.iterationData.get("expectedStatus"));
const query = pm.iterationData.get("query");

pm.test("query=" + query + " → HTTP " + expectedStatus, function () {
  pm.expect(pm.response.code).to.equal(expectedStatus);
});

if (expectedStatus === 200) {
  pm.test("query=" + query + " → sonuç var ve sorgu yansıyor", function () {
    const body = pm.response.json();
    pm.expect(body.meta.pagination.query).to.equal(query);
    pm.expect(body.meta.pagination.total_items).to.be.at.least(1);
    pm.expect(body.data).to.be.an("array").that.is.not.empty;
  });
} else {
  pm.test("query=" + query + " → hata gövdesi mesaj içeriyor", function () {
    pm.expect(pm.response.json().message).to.be.a("string").that.is.not.empty;
  });
}
Kodun açıklaması
  • CSV değerleri metin gelir; bu yüzden Number(...) ile sayıya çeviriyoruz. JSON dosyasında sayılar sayı olarak gelir, ama dönüşüm zararsızdır.
  • pm.info.iteration — şu anki iterasyonun sıfırdan başlayan numarası; test adına eklemek raporu okunur yapar.
  • expectedStatus sütunu: aynı test kodu hem pozitif (200) hem negatif (404) satırları doğrular — beklenen sonuç veride durur.
  • Toplam sonuç sayısını sabit assert etmedik; at.least(1) kullandık (katalog değişebilir).

7.6Script hatalarını ayıklama

Bu konu nedir?

Postman'da script hatalarını görmenin üç yolu vardır: Console (console.log/info/warn/error), Test Results (kırmızı testler) ve isteğin yanıt alanında çıkan script hata uyarısı. Hata kategorileri: sözdizimi (kod çalışmaz), çalışma zamanı (tanımsız alan), mantık (yanlış beklenti).

Neden önemlidir?

Test kodunda hata yapmak kaçınılmazdır; hata ayıklama hızı, bakım maliyetini belirler. Savunmacı kod (try/catch, guard) “kırmızı ama neden belli değil” durumunu azaltır.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Her otomasyon projesiCI'da kırmızı build'in %30'u test kodu hatasıdır; Console günlüğü ve anlamlı test adı çözümü hızlandırır.
  • Dağıtık test yazan ekiplerOrtak helper'lar hatalıysa yüzlerce test aynı anda düşer.

Hangi durumlarda?

  • Test kodu yazarken.
  • CI'da test kodu kaynaklı kırmızılar çıkınca.
  • Yanıt JSON dışı geldiğinde.
Kod örneği
JavaScriptPost-response — savunmacı JSON okuma ve günlükleme
// Savunmacı JSON okuma: yanıt JSON değilse kontrollü hata ver
function safeJson() {
  try {
    return pm.response.json();
  } catch (e) {
    console.error("JSON ayrıştırılamadı. Durum:", pm.response.code, "| İlk 120 karakter:", pm.response.text().slice(0, 120));
    return null;
  }
}

const body = safeJson();

pm.test("Yanıt JSON olarak okunabiliyor", function () {
  pm.expect(body, "gövde JSON olmalı").to.not.equal(null);
});

if (body) {
  console.log("İstek:", pm.info.requestName, "| iterasyon:", pm.info.iteration, "| durum:", pm.response.code);
}
Kodun açıklaması
  • try/catch — pm.response.json() JSON olmayan gövdede hata fırlatır; yakalayıp console.error ile bağlamı (durum + ilk karakterler) yazıyoruz.
  • Test, null durumunda kırmızı olur: script çökmez, nedeni okunabilir bir test başarısızlığı olarak görünür.
  • pm.info.requestName / pm.info.iteration — Console'da hangi istekten, hangi iterasyondan geldiğini ayırt etmeyi sağlar.
Postman'da uygulama
  1. Alt çubuktan Console'u açın ve yukarıdaki kodu bir isteğin Post-response'una yapıştırıp gönderin.
  2. Sözdizimi hatası üretin: son } karakterini silin, gönderin: hatayı Console'da ve yanıt alanında görün; düzeltin.
  3. Çalışma zamanı hatası: body.data[0].id yerine body.veri[0].id yazın; TypeError mesajını okuyun; düzeltin.
  4. JSON olmayan yanıt: URL'yi bir HTML sayfasına (https://example.com) çevirip kodu çalıştırın; testin kırmızı olduğunu ve Console'daki açıklamayı görün.

Postman 12.34.3: ne yapalım, ne yapmayalım?

Yapın
  • Her istek için test adına bağlam koyun (satır, parametre).
  • Hata ayıklarken console.log kullanın; işiniz bitince gürültüyü silin.
Yapmayın
  • Token/parola gibi sırları console.log ile yazdırmayın.
  • Hata mesajını okumadan kodu rastgele değiştirmeyin.

7.7Tekrar kullanılabilir test kodu: yardımcılar, collection scriptleri ve paketler

Bu konu nedir?

Test kodunu tekrar kullanmanın üç düzeyi vardır: (1) tek script içinde yardımcı fonksiyon, (2) collection/folder düzeyi script (her isteğe uygulanır), (3) ekip paketleri (Postman Package Library; ekibe paylaşılan, istekler arasında kullanılan kodlar). Paket kullanılabilirliği Postman planına bağlıdır; ayrıntılar için Package Library yardımı sayfasına bakın.

Neden önemlidir?

Aynı doğrulama 40 yerde kopyalanırsa kuralı değiştirmek 40 düzenleme demektir. Tek yerde yaşayan kod, bakım maliyetini düşürür; ama paylaşılan kodda hata yüzlerce testi birden bozar: küçük, test edilmiş ve belgelenmiş tutun.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Büyük test paketleriOrtak assertion'lar (zarf yapısı, sayfalama kuralı) yüzlerce istekte aynıdır.
  • Birden çok ekibin ortak kullandığı API'lerOrtak paket, tüm ekiplerin aynı sözleşme kontrolünü kullanmasını sağlar.

Hangi durumlarda?

  • Aynı kod ikinci kez kopyalandığında.
  • Ortak kural değiştiğinde.
  • Ekipler arası standardizasyon gerektiğinde.
Kod örneği
JavaScriptPost-response — yerel yardımcı fonksiyonlar (GET /api/posts?page=1&per_page=2)
// Yardımcı fonksiyonlar: tek bir scriptte tekrarı azaltır
function expectPaginatedList(body, perPage) {
  pm.expect(body.data, "data").to.be.an("array");
  pm.expect(body.data.length, "data.length").to.be.at.most(perPage);
  pm.expect(body.meta.pagination.per_page, "per_page").to.equal(perPage);
}

function testEach(items, label, check) {
  items.forEach(function (item, index) {
    pm.test(label + " #" + (index + 1), function () { check(item); });
  });
}

const body = pm.response.json();
const perPage = Number(pm.request.url.query.get("per_page"));

pm.test("Liste sayfalama kurallarına uyuyor", function () {
  expectPaginatedList(body, perPage);
});

testEach(body.data, "Gönderi alanları", function (post) {
  pm.expect(post.id).to.be.a("number");
  pm.expect(post.title).to.be.a("string").that.is.not.empty;
});
Kodun açıklaması
  • expectPaginatedList — sayfalama kuralını tek yerde tutar; farklı liste isteklerinde aynı kural kullanılır.
  • testEach — listedeki her eleman için ayrı bir test satırı üretir: hangi elemanın hatalı olduğu raporda görünür.
  • Yardımcı fonksiyonlar yalnızca aynı script içinde yaşar; birden çok istek için collection düzeyi script ya da Package Library gerekir.
Beklenen sonuç

GET /api/posts?page=1&per_page=2 isteğinde 1 + 2 = 3 test geçer (1 sayfalama + 2 gönderi).

Bölüm özeti

  • Pre-request script, istek içeriğini koşu anında hazırlar: dinamik değişkenler, izleme başlıkları, yapay veri.
  • Tarih/sayı/metin doğrulaması iş kuralını sınar; sözleşmede olmayan aralıklar ekip kuralı olarak etiketlenir.
  • Zincirleme test: yanıttan alınan değer collection değişkeni ile taşınır; ID'ler koda gömülmez.
  • pm.execution.setNextRequest(null) koşuyu durdurur, pm.execution.skipRequest() isteği atlar; yalnızca toplu koşuda etkilidir.
  • Veri odaklı test: CSV/JSON her satır → bir iterasyon; beklenen sonuç veride durur (expectedStatus).

Sonraki bölüme hazırlık: Ders 8'de güvenlik ve performans kontrollerini otomatikleştireceğiz: yetkisiz erişim senaryolarını sürekli koşulabilir hale getirmek, yanıtlarda hassas veri taramak, girdi doğrulama testleri ve yanıt süresi eşikleri.
