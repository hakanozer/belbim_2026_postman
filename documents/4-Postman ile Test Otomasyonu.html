Postman ile API Testi (Test Otomasyonu) Eğitimi

4Postman ile Test Otomasyonu

Elle yaptığınız doğrulamayı koda döküyoruz: Postman'da test script'lerinin yazıldığı yeri öğreniyor, pm.test() ve pm.expect() ile durum kodunu, header'ları, JSON alanlarını ve iş kurallarını otomatik doğruluyor, başarısız testi okuyup düzeltiyoruz.

  • Seviye: Orta
  • Süre: ~120 dk
  • Ön koşul: Ders 2–3
  • Gerekli: kayıtlı GET istekleri
Önceki bölüm3. API Test Senaryoları ve Test Tasarımı
Sonraki bölüm5. Kimlik Doğrulama ve Yetkilendirme

Bu bölümün öğrenme hedefleri

Scripts → Pre-request ve Post-response sekmelerini ayırt etmek.
pm.test, pm.expect, pm.response ile durum, header ve gövde doğrulamak.
Pozitif ve negatif yanıt için ayrı test yazmak; JSON şemasıyla sözleşme doğrulamak.
Başarısız testin hata mesajını okuyup nedenini (istek / servis / test) ayırt etmek.
Sekme adları (v12)

Güncel ad–eski ad notu. Postman v12 yardımında istek scriptleri Scripts sekmesi altında Pre-request (gönderimden önce) ve Post-response (yanıttan sonra) olarak adlandırılır. Eski kaynaklarda Tests sekmesinden söz edilir; yanıttan sonra çalışan test kodunun yeri artık Scripts → Post-response'tur. Test sonuçları yanıt alanındaki Test Results sekmesinde görünür.

GraphQL ve gRPC isteklerinde hook adları farklıdır (Before query / After response, Before invoke / On message / After response); bu eğitimde yalnızca HTTP isteklerini kullanıyoruz.

4.1Test otomasyonunun amacı ve script alanları

Bu konu nedir?

Test otomasyonu, elle yaptığınız “gözle kontrol”ü bir kod parçasına çevirip her çalıştırmada aynı kriterlerle tekrar etmektir. Postman'da bu kod, istek yanıtı geldikten sonra Scripts → Post-response sekmesinde çalışır; sonuçlar Test Results sekmesinde geçti/kaldı olarak görünür.

Neden önemlidir?

Kural sade: elle iki kez yaptığınız doğrulama otomatikleşmeye adaydır. Otomasyon kalitesi, insan dikkatini gerektiren sürekli kontrolü ortadan kaldırır ve sonucun yorumlanabilir olmasını sağlar.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Bankacılık / sigortaHer sürüm öncesi yüzlerce servis kontrolü regresyon paketinde yürür; manuel kontrol imkânsızdır.
  • E-ticaretKampanya öncesi kritik akışların (katalog, sepet, ödeme) yanıtları otomatik doğrulanır.
  • Platform / entegrasyon ekipleriServis sahipleri sözleşme testlerini tüketici ekiplerle paylaşır; kırılma değişiklik anında görünür.

Hangi durumlarda?

  • Aynı doğrulamayı ikinci kez yaptığınız anda.
  • Her pull request ve sürüm kapısında.
  • Üretimde bulunan bir hatanın regresyon testi eklenirken.
Postman'da uygulama
  1. Kayıtlı GET Posts - liste (sayfalı) isteğini (Ders 2) açın.
  2. İstek sekmelerinden Scripts'e tıklayın.
  3. Pre-request ve Post-response alt sekmelerini görün; bu derste yalnızca Post-response'u kullanacağız.
  4. Editörün sağ altında Snippets simgesini (kod simgesi) ve Beautify düğmesini bulun: Snippets hazır kod parçaları ekler, Beautify kodu biçimlendirir.

Postman 12.34.3: ne yapalım, ne yapmayalım?

Yapın
  • Test kodunu Post-response sekmesine yazın.
  • Kodu yazdıktan sonra Save ile isteği kaydedin; kaydedilmeyen script CI'da yoktur.
Yapmayın
  • Test kodunu Pre-request sekmesine yazmayın: yanıt henüz yoktur, pm.response tanımsızdır.
  • Collection düzeyindeki bir scripti yanlışlıkla her request'e etki edecek şekilde bırakmayın (etkisini önceden düşünün).
Hata durumları ve çözümleri
BelirtiNedenÇözüm
pm.response is undefinedKod Pre-request sekmesinde.Post-response sekmesine taşıyın.
Test Results boşScript kaydedilmemiş ya da hiç pm.test yok.Kaydedin, isteği yeniden gönderin.
Eski kaynaktaki tests[...] sözdizimiEski (legacy) yazım.pm.test() ve pm.expect() ile yeniden yazın.

4.2JavaScript'e hızlı başlangıç: değişken, tip, dizi, nesne, koşul, fonksiyon

Bu konu nedir?

Postman scriptleri JavaScript'tir (Postman Sandbox, Node.js tabanlı bir çalışma ortamı). Test yazmak için JavaScript'in küçük bir alt kümesi yeterlidir: değişkenler, temel tipler, diziler, nesneler, koşullar ve fonksiyonlar.

Neden önemlidir?

Test kodunun %90'ı JSON'da yol bulup değer karşılaştırmaktır. Tipleri ve dizi/nesne erişimini rahat okuyabilmek, hata ayıklama süresini yarıya indirir.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Her otomasyon ekibiPostman scriptleri, CI'daki Newman/CLI koşuları ve API istemci kodları aynı JavaScript bilgisini kullanır.
  • Manuel testten otomasyona geçenlerKüçük bir JavaScript temeli, “kopyala–yapıştır” bağımlılığını kırar.

Hangi durumlarda?

  • İlk kez test scripti yazarken.
  • JSON yanıtında iç içe alan okurken.
  • Basit yardımcı fonksiyon yazarken.
Uygulamaya hazırlık

Önceki konudaki isteğin Scripts → Post-response sekmesini açın. Bu örnek bir test değil; yalnızca Console'a çıktı üretir.

Kod örneği
JavaScriptScripts → Post-response — JavaScript temelleri
// JavaScript temelleri — çıktıyı Console'da göreceğiz
const baseUrl = "https://jsonbulut.com";   // string (metin)
const pageSize = 2;                        // number (sayı)
const readOnly = true;                     // boolean (mantıksal)
const ids = [1, 2, 3];                     // array (dizi)
const post = { id: 1, title: "örnek" };    // object (nesne)

function isPositive(n) {
  return typeof n === "number" && n > 0;
}

if (isPositive(pageSize)) {
  console.log("pageSize geçerli:", pageSize);
} else {
  console.log("pageSize geçersiz");
}

const doubled = ids.map(function (n) { return n * 2; });
console.log("Dizi uzunluğu:", ids.length);
console.log("Başlık uzunluğu:", post.title.length);
console.log("İki katı:", doubled.join(", "));
console.log("Salt okunur mu?", readOnly, "| Taban adres:", baseUrl);
Kodun açıklaması
  • const — yeniden atanamayan değişken; let yeniden atanabilir. Yeni kodda var kullanmayın.
  • string, number, boolean — temel tipler; [ ] dizi (sıralı liste), { } nesne (anahtar–değer).
  • typeof n === "number" — tip denetimi; === tip ve değeri birlikte karşılaştırır (== kullanmayın).
  • if … else — koşul; function isPositive(n) — yeniden kullanılabilir küçük kod parçası.
  • ids.map(...) — dizinin her elemanına işlem uygulayıp yeni dizi üretir; join diziyi metne çevirir.
  • console.log(...) — Postman Console'a yazar; test sonucu üretmez.
Beklenen sonuç

Console'da (alt çubuk → Console) şu satırları görürsünüz: pageSize geçerli: 2, Dizi uzunluğu: 3, Başlık uzunluğu: 5, İki katı: 2, 4, 6, Salt okunur mu? true | Taban adres: https://jsonbulut.com. Test Results sekmesinde test olmadığından 0 test görünür.

Hata durumları ve çözümleri
BelirtiNedenÇözüm

4.3İlk otomatik test: pm.test, pm.expect ve pm.response.code

Bu konu nedir?

**pm.test(ad, fonksiyon) bir test tanımlar ve adıyla Test Results'a yazar. pm.expect(değer)** Chai tarzı bir beklenti kurar: pm.expect(gerçek).to.equal(beklenen). **pm.response** son yanıtı temsil eder; pm.response.code HTTP durum kodu, pm.response.json() gövdenin JSON hâlidir.

Neden önemlidir?

Test adı, CI raporunun ve hata triyajının dilidir: “Test 3 başarısız” yerine “HTTP durum kodu 200” demek, sorunu okumadan anlatır. Beklenti kodu da sözleşmenin çalışan hâlidir.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Her API test paketiDurum kodu ve gövde kök alanı, en ucuz ve en güvenilir doğrulamalardır; her isteğin ilk iki testi olur.
  • Sözleşme tüketicileriGövdenin data alanını beklemek, istemci kodunun varsayımını testle sabitlemektir.

Hangi durumlarda?

  • Her yeni istek otomasyona alınırken.
  • Yeni sürümde yanıt zarfı değişmiş mi diye bakarken.
  • Hata sonrası regresyon testi eklerken.
Uygulamaya hazırlık
  • İstek: GET {{baseUrl}}/api/posts?page=1&per_page=2 — henüz environment tanımadıysanız https://jsonbulut.com/api/posts?page=1&per_page=2 adresini kullanın.
  • Bağımlılık: yanıtın meta + data zarfı (Ders 1).
  • Beklenen sonuç: iki test, ikisi de geçer.
Postman'da uygulama
  1. İsteği açın → Scripts → Post-response sekmesi.
  2. Aşağıdaki kodu tamamen yapıştırın (varsa eski içeriği silin).
  3. Save'e tıklayın.
  4. Send'e tıklayın.
  5. Yanıt alanında Test Results sekmesine tıklayın: sekme başlığında 2/2 gibi geçen/toplam sayısını göreceksiniz.
JavaScriptScripts → Post-response — ilk iki test
pm.test("HTTP durum kodu 200", function () {
  pm.expect(pm.response.code).to.equal(200);
});

pm.test("Yanıt JSON ve 'data' bir dizi", function () {
  const body = pm.response.json();
  pm.expect(body).to.have.property("data");
  pm.expect(body.data).to.be.an("array");
});
Kodun açıklaması
  • pm.test(ad, function () { ... }) — ilk argüman Test Results'ta görünen test adıdır; fonksiyon içindeki beklenti geçerse test yeşil, hata fırlatırsa kırmızı olur.
  • pm.expect(pm.response.code).to.equal(200) — gerçek değer (pm.response.code) beklenen değere (200) eşit olmalı.
  • const body = pm.response.json() — yanıt gövdesini JSON nesnesine çevirir; gövde JSON değilse hata fırlatır ve test kırmızı olur.
  • to.have.property("data") — nesnede data anahtarı var mı; to.be.an("array") — tipi dizi mi.
  • Alternatif yazım: pm.response.to.have.status(200) aynı kontrolü tek satırda yapar; biz beklenen/gerçek ayrımı açık olsun diye pm.expect kullanıyoruz.
Beklenen sonuç

Test Results sekmesinde iki satır ve yanında geçti göstergesi: HTTP durum kodu 200 ve Yanıt JSON ve 'data' bir dizi. Sekme başlığı 2/2 (veya sürümünüzdeki eşdeğer ifade) olmalıdır.

Sonuç nasıl doğrulanır?

Başarıyı durum kodu (200) ve gövde şekli (data dizi) birlikte kanıtlar. Yalnızca durum koduna bakan bir test, 200 dönen ama bozuk gövdeli yanıtı kaçırır.

Hata durumları ve çözümleri
BelirtiNedenÇözüm
Test Results 0/0Script kaydedilmedi / yanlış sekmeye yazıldı.Post-response'a yazıp Save ve Send.
Unexpected token < in JSONGövde JSON değil (HTML hata sayfası).Önce durum kodunu ve content-type header'ını inceleyin.
AssertionError: expected undefined to be an arrayZarf yolu yanlış (body.data yok).Gövdeyi Body sekmesinde kontrol edin; yolu düzeltin.
Uygulama alıştırması

Kodu açıp to.equal(200) değerini bilerek 201 yapın ve isteği tekrar gönderin. Hata mesajını okuyun (Konu 4.7'de ayrıntılı işleyeceğiz); sonra düzeltin.

4.4pm.response: header, süre ve içerik tipi doğrulama

Bu konu nedir?

Yanıtın yalnızca gövdesi değil, header'ları da sözleşmenin parçasıdır. pm.response.headers.get("Ad") header değerini döndürür (ad büyük/küçük harfe duyarsızdır); pm.response.responseTime isteğin yanıt süresini milisaniye olarak verir.

Neden önemlidir?

Yanlış Content-Type ile gelen bir yanıt istemcileri sessizce bozar; cache başlıkları ise güvenlik ve performans için kritiktir. Header testleri ucuzdur, hataları erken yakalar.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Güvenlik / uyumCache-Control, Content-Type ve güvenlik başlıkları (Ders 8) denetim maddesidir.
  • CDN / ağ geçidi arkasındaki servislerAra katmanlar header'ları değiştirebilir; regresyon testi bunu yakalar.

Hangi durumlarda?

  • İstemcinin parse davranışı header'a bağlıysa.
  • Cache stratejisi doğrulanırken.
  • Ağ geçidi/proxy değişikliklerinden sonra.
Kod örneği
JavaScriptScripts → Post-response — header testleri
pm.test("Content-Type application/json içeriyor", function () {
  const contentType = pm.response.headers.get("Content-Type");
  pm.expect(contentType).to.be.a("string");
  pm.expect(contentType).to.include("application/json");
});

pm.test("Date header'ı mevcut", function () {
  pm.expect(pm.response.headers.has("Date")).to.be.true;
});
Kodun açıklaması
  • headers.get("Content-Type") — header değerini metin olarak okur; header yoksa undefined döner, bu yüzden önce tipini doğruluyoruz.
  • include("application/json") — tam eşitlik yerine içerme: servis ; charset=utf-8 ekleyebilir; bu kırılgan bir testi önler.
  • headers.has("Date") — header var mı (true/false).
Beklenen sonuç

Test Results'ta iki yeni test geçer. Gözlenen header değeri: content-type: application/json (29 Ekim 2026).

Hata durumları ve çözümleri
BelirtiNedenÇözüm
expected undefined to be a stringHeader yok veya adı yanlış.Headers sekmesindeki gerçek adı kontrol edin.
Test geçiyor ama gövde bozukHeader testi gövdeyi kapsamaz.Gövde testlerini de ekleyin (sonraki konu).

4.5Gövde doğrulama: alanlar, tipler ve iş kuralı

Bu konu nedir?

Gövde testleri üç katmanda yazılır: var mı (yapı), ne tip (tip), mantıklı mı (iş kuralı). Aşağıda gönderi listesi için hem alan/tip hem sayfalama tutarlılığı doğrulanır.

Neden önemlidir?

Yapı ve tip testleri, istemci kodunun kırılmasını yakalar; iş kuralı testleri ise “200 ama yanlış veri” hatalarını yakalar (örn. toplam sayfa sayısı hesaplanmıyor).

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Katalog ve liste servisleriSayfalama toplamları, filtre sonuçları ve sıralama kurallarında hata sık görülür.
  • Fiyat/komisyon hesaplayan servislerTutar alanlarının tipi ve iş kuralı (yuvarlama, aralık) doğrudan finansal etkidir.

Hangi durumlarda?

  • Yeni alan eklenince.
  • Veri modeli değişikliğinde.
  • Hesaplanan alanlar (toplam, yüzde) olduğunda.
Uygulamaya hazırlık
  • İstek: GET https://jsonbulut.com/api/posts?page=1&per_page=2 (query'de değişken kullanmayın; kod sorgudan okur).
  • Bağımlılık: meta.pagination ve data[*] (id, title, body) alanları (Ders 1'de gözlendi).
Kod örneği
JavaScriptScripts → Post-response — gövde ve iş kuralı testleri
pm.test("Her gönderi beklenen alanlara ve tiplere sahip", function () {
  const body = pm.response.json();
  pm.expect(body.data).to.be.an("array").that.is.not.empty;
  body.data.forEach(function (post) {
    pm.expect(post.id, "id").to.be.a("number");
    pm.expect(post.title, "title").to.be.a("string").that.is.not.empty;
    pm.expect(post.body, "body").to.be.a("string");
  });
});

pm.test("Sayfalama bilgisi iş kuralıyla tutarlı", function () {
  const body = pm.response.json();
  const pagination = body.meta.pagination;
  const requestedPerPage = Number(pm.request.url.query.get("per_page"));

  pm.expect(pagination.per_page).to.equal(requestedPerPage);
  pm.expect(body.data.length).to.be.at.most(pagination.per_page);
  pm.expect(pagination.total_pages).to.equal(Math.ceil(pagination.total_items / pagination.per_page));
});
Kodun açıklaması
  • .that.is.not.empty — dizi/metin boş olmamalı.
  • forEach — listedeki her elemanı doğrular; yalnızca ilkine bakmak kısmi güven verir.
  • pm.expect(değer, "id") — ikinci argüman hata mesajına eklenir: hangi alanın hatalı olduğunu söyler.
  • pm.request.url.query.get("per_page") — gönderilen isteğin sorgu parametresini okur; böylece beklenen değeri koda sabit yazmayız.
  • Math.ceil(total_items / per_page) — iş kuralı: toplam sayfa sayısı yukarı yuvarlanmış bölüm olmalı (gözlem: 100/2 → 50).
  • at.most(n) — en fazla n.
Beklenen sonuç

İki test de geçer. Gözlem: per_page = 2, total_items = 100, total_pages = 50, data.length = 2.

Hata durumları ve çözümleri
BelirtiNedenÇözüm
expected 'NaN' ...Sorguda per_page yok (Number(null) = 0 / NaN).İsteğe per_page ekleyin ya da kodda varsayılan değer verin.
id: expected '1' to be a numberAlan tipi string olarak geliyor.Sözleşmeyi API sahibiyle netleştirin; gerekirse Number(...) kullanın ama tip kaymasını bulgu olarak kaydedin.
Test URL değişkenine takılıyorpm.request.url.query çözülmemiş {{...}} içeriyor.Beklenen değeri değişkenden okuyun (pm.variables.get) — Ders 6.

4.6Negatif yanıt testleri: 404 ve 401

Bu konu nedir?

Negatif test, hata yanıtının beklenen hata olduğunu doğrular: doğru durum kodu, hata gövdesi, ve gövdede veri sızmaması. JSONBulut'ta iki gerçek örnek: olmayan ürün (404, sözleşmede tanımlı) ve token'sız profil (401, sözleşmede tanımlı).

Neden önemlidir?

Hata davranışı, istemcinin kullanıcı deneyimini belirler. Ayrıca yetkisiz erişimin gerçekten reddedildiğini otomatik kanıtlamak, güvenlik denetiminin ucuz bir parçasıdır.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Bankacılık / sigortaBaşkasının hesabı/poliçesi için istek yapıldığında 403/404 dönmesi ve veri sızmaması zorunlu güvenlik kontrolüdür.
  • Mobil / web istemcileri401'de oturumu yenileme, 404'te “bulunamadı” ekranı gösterme davranışı sunucunun doğru kodu döndürmesine bağlıdır.

Hangi durumlarda?

  • Her kaynağın “yok” ve “yetkisiz” senaryosu için.
  • Yetki modeli değiştiğinde.
  • Hata sözleşmesi standardize edilirken.
Uygulamaya hazırlık
  • İstek A: GET https://jsonbulut.com/api/products/99999 (kimliksiz).
  • İstek B: GET https://jsonbulut.com/api/profile/me — Authorization: No Auth, yalnızca izinli test ortamı.
  • Bu isteklerde gövde ve token gönderilmez.
Kod örneği
JavaScriptİstek A — GET /api/products/99999
// İstek A — GET /api/products/99999  → Scripts → Post-response
pm.test("Olmayan ürün için 404 döner", function () {
  pm.expect(pm.response.code).to.equal(404);
});

pm.test("404 gövdesi JSON ve ürün verisi içermiyor", function () {
  const body = pm.response.json();
  pm.expect(body).to.not.have.property("data");
  pm.expect(body.meta.status).to.equal(404);
});
JavaScriptİstek B — GET /api/profile/me
// İstek B — GET /api/profile/me (token yok)  → Scripts → Post-response
pm.test("Token olmadan 401 döner", function () {
  pm.expect(pm.response.code).to.equal(401);
});

pm.test("401 yanıtı mesaj içeriyor, profil verisi içermiyor", function () {
  const body = pm.response.json();
  pm.expect(body.message).to.be.a("string").that.is.not.empty;
  pm.expect(body).to.not.have.property("data");
});
Kodun açıklaması
  • to.not.have.property("data") — hata yanıtında başarılı yanıtın veri alanı olmamalı.
  • body.meta.status — bu servisin 404 gövdesinde meta.status bulunuyor (gözlem); farklı bir hata gövdesi (401'deki message) olduğuna dikkat edin: iki hata biçimi iki ayrı test gerektirir.
  • Mesaj metnini birebir ("Token is Invalid!") assert etmedik; sözleşmede yok. Yalnızca mesajın var ve boş olmadığını doğruladık.
Beklenen sonuç

Her iki istekte de iki test geçer. Gözlem: A → 404 {"meta":{"status":404,"message":"Not Found"}}; B → 401 {"message":"Token is Invalid!"}.

4.7Başarısız testi okumak: hata mesajı, Refresh results ve Console

Bu konu nedir?

Başarısız test bir sorun değil, bir bilgidir: nerede beklentinin gerçekle ayrıştığını söyler. Postman, gerçek ve beklenen değeri hata mesajında gösterir (expected 200 to equal 201).

Neden önemlidir?

Başarısızlığın nedeni üç kategoriden biridir: (1) servis değişti/bozuldu, (2) istek yanlış kuruldu, (3) test yanlış varsayım yapıyor. Doğru sınıflama, aksiyonu belirler: kusur kaydı mı, istek düzeltmesi mi, test güncellemesi mi?

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • CI/CD hattı olan ekiplerKırmızı build'in ilk beş dakikası genellikle “neden kırmızı?” sorusuna harcanır; hata mesajını doğru okumak MTTR'ı düşürür.
  • Test bakım yüküKırılgan testlerin çoğu aşırı sıkı varsayımlardan (sabit ID, sabit toplam) kaynaklanır.

Hangi durumlarda?

  • Her kırmızı testte.
  • Yeni sürümde beklenmeyen kırılma olduğunda.
  • Test kodu refactor edilirken.
Kod örneği
JavaScriptBilerek başarısız test — yalnızca öğrenme amaçlı
pm.test("YANLIŞ BEKLENTİ: 201 bekliyoruz (bilerek başarısız)", function () {
  pm.expect(pm.response.code).to.equal(201);
});
Postman'da uygulama
  1. GET Posts - liste (sayfalı) isteğinin Post-response sekmesine yukarıdaki testi ek olarak yapıştırın ve Send'e tıklayın.
  2. Test Results sekmesinde kırmızı satırı bulun; hata mesajını okuyun.
  3. Alt çubuktan Console'u açıp aynı isteğin gerçek durum kodunu görün.
  4. Beklentiyi 200'e düzeltin; isteği yeniden göndermeden sonucu güncellemek için Test Results sağ üstündeki Refresh results düğmesine tıklayın: Postman, son yanıt üzerinde yeni test kodunu çalıştırır; sunucuya yeni istek gitmez.
  5. Sonuç yeşile döndüğünde, deneme testini silin.

Postman 12.34.3: ne yapalım, ne yapmayalım?

Yapın
  • Önce gerçek durum kodunu ve gövdeyi okuyup sorunun hangi kategoride olduğuna karar verin.
  • Yazma isteklerinde (POST/PUT/DELETE) test kodunu düzeltirken Refresh results kullanın; isteği tekrar göndermek kaydı tekrar oluşturur/siler.
Yapmayın
  • Kırmızı testi yeşil yapmak için beklentiyi gerçek değerin aynısına çekmeyin (testi anlamsız kılar).
  • Hatayı anlamadan testi silmeyin ya da yorum satırı yapmayın.
Beklenen sonuç

Kırmızı satırda şuna benzer bir ifade: AssertionError: expected 200 to equal 201. Soldaki sayı gerçek, sağdaki sayı beklenen değerdir. Düzeltmeden sonra aynı satır yeşildir.

4.8Sözleşme doğrulama (JSON Schema) ve collection düzeyinde ortak test

Bu konu nedir?

JSON Schema, bir yanıtın şeklini (alanlar, tipler, zorunluluk) tanımlayan standarttır. Postman'da pm.response.to.have.jsonSchema(şema) ile yanıt tek seferde şemaya karşı doğrulanır. Collection düzeyinde test, tek bir script'in collection'daki her isteğe uygulanmasıdır.

Neden önemlidir?

Alan alan pm.expect yazmak, 30 alanlı bir yanıtta yorucudur. Şema, sözleşmeyi tek yerde tutar. Ortak testler ise her isteğe tekrar tekrar kopyalanmaz.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Servis sahibi / tüketici ekiplerContract testing: servis sahibi şemayı yayımlar; tüketici ekip yanıtın şemaya uyduğunu otomatik doğrular.
  • Büyük katalog / profil nesneleriÇok alanlı nesnelerde sürümler arası alan kaybını yakalamanın en ucuz yoludur.

Hangi durumlarda?

  • Yanıt nesnesi çok alanlıysa.
  • Sürüm sonrası uyumluluk kontrolünde.
  • Aynı kuralı her isteğe uygulamak isteyince (header, süre).
Uygulamaya hazırlık
  • İstek: GET https://jsonbulut.com/api/products/1 (kimliksiz). Gözlenen alanlar: id, title, description, category, price, discountPercentage, rating, stock, tags, brand, sku, minimumOrderQuantity, images (OpenAPI Product şemasıyla aynı).
  • Şemada yalnızca bağımlı olduğumuz alanları required yaptık; fazlasını beklemek kırılgan olur.
Kod örneği
JavaScriptScripts → Post-response — GET /api/products/1
const productSchema = {
  type: "object",
  required: ["meta", "data"],
  properties: {
    meta: { type: "object", required: ["status"], properties: { status: { type: "integer" } } },
    data: {
      type: "object",
      required: ["id", "title", "price", "category", "stock", "tags", "images"],
      properties: {
        id: { type: "integer" },
        title: { type: "string" },
        price: { type: "number" },
        category: { type: "string" },
        stock: { type: "integer" },
        tags: { type: "array", items: { type: "string" } },
        images: { type: "array", items: { type: "string" } }
      }
    }
  }
};

pm.test("Ürün yanıtı JSON şemasına uyuyor", function () {
  pm.response.to.have.jsonSchema(productSchema);
});
JavaScriptCollection → Scripts → Post-response — ortak testler
// COLLECTION düzeyi: collection adına tıklayın → Scripts → Post-response
pm.test("Yanıt JSON içerik tipinde", function () {
  pm.expect(pm.response.headers.get("Content-Type")).to.include("application/json");
});

pm.test("Yanıt süresi eşiğin altında", function () {
  const limit = Number(pm.collectionVariables.get("maxResponseMs") || 3000);
  pm.expect(pm.response.responseTime).to.be.below(limit);
});
Kodun açıklaması
  • required: [...] — bu alanlar bulunmak zorunda; listede olmayan ek alanlar sorun sayılmaz (esneklik).
  • type: "integer" / "number" — id tam sayı, price ondalıklı olabilir.
  • pm.response.to.have.jsonSchema(...) — şema ihlalinde hangi alanın neden hatalı olduğunu mesajda gösterir.
  • pm.collectionVariables.get("maxResponseMs") — collection değişkeni; yoksa || 3000 ile varsayılan eşik (Ders 6'da tanımlayacağız).
  • Collection düzeyi script, her isteğin ardından çalışır: bu yüzden yalnızca tüm isteklerde geçerli kuralları buraya koyun.
Postman'da uygulama
  1. GET Products - detay isteğini (/api/products/1) oluşturun; Scripts → Post-response'a şema testini yapıştırın; Save ve Send.
  2. Kenar çubuğunda collection'a tıklayın; iş alanında Scripts sekmesini ve Post-response'u açın; ortak testleri yapıştırın.
  3. Collection içindeki herhangi bir isteği gönderin: Test Results'ta request testlerinin yanında collection testlerini de görün.

Postman 12.34.3: ne yapalım, ne yapmayalım?

Yapın
  • Şemaya yalnızca sözleşmenin gerçekten güvence verdiği alanları koyun.
  • Ortak (collection düzeyi) testleri küçük ve her istek için geçerli tutun.
Yapmayın
  • Gözlenen her alanı required yapmayın; küçük bir ekleme/silme gereksiz kırılma üretir.
  • Her isteğe uymayan bir kuralı collection düzeyine koymayın (ör. data dizisi bekleyen test).
Beklenen sonuç

Ürün detayında şema testi geçer. Collection testleri, isteklerin Test Results sekmesine eklenir.

Hata durumları ve çözümleri
BelirtiNedenÇözüm

Bölüm özeti

  • Test kodu Scripts → Post-response sekmesinde yazılır; sonuçlar yanıt alanındaki Test Results'ta, console.log çıktıları Console'da görünür.
  • pm.test(ad, fn) testi tanımlar; pm.expect(gerçek).to... beklenti kurar; pm.response.code/json()/headers/responseTime yanıtı okur.
  • Gövde testleri yapı → tip → iş kuralı katmanlarında yazılır; negatif testler kod, gövde ve veri sızıntısı yokluğunu doğrular.
  • Başarısız testi önce kategorize edin: servis mi, istek mi, test mi? Refresh results yeni istek göndermeden testi yeniden çalıştırır.
  • JSON Schema ve collection düzeyi testler tekrarı azaltır.

Sonraki bölüme hazırlık: Ders 5'te kimlik doğrulamayı ele alıyoruz: Bearer/JWT'nin ne olduğunu, JSONBulut'ta hangi uçların token istediğini ve token'ı güvenle nasıl yöneteceğimizi göreceksiniz. Hazırlık: Ders 4'teki N-02 (GET /api/profile/me, No Auth) isteğiniz kayıtlı olsun.

Bölüm sonu uygulaması

S-01'e bilerek hatalı bir beklenti ekleyin, hata mesajını yorumlayın, Refresh results ile düzeltin.

✓Bölüm sonu öğrenme kontrolü

  1. Test kodunu neden Pre-request değil Post-response sekmesine yazarız?
    Cevabı göster
    Çünkü yanıt Pre-request aşamasında yoktur; pm.response yalnızca yanıttan sonra tanımlıdır.
  2. pm.expect(a).to.equal(b) ifadesinde hangisi gerçek, hangisi beklenen değerdir?
    Cevabı göster
    a gerçek (gözlenen) değer, b beklenen değerdir.
  3. Header testinde neden equal yerine include kullandık?
    Cevabı göster
    Content-Type değeri ; charset=utf-8 gibi eklerle gelebilir; tam eşitlik kırılgan olur.
  4. Refresh results ne yapar, ne zaman işe yarar?
    Cevabı göster
    Son yanıt üzerinde Post-response scriptini yeniden çalıştırır, sunucuya yeni istek göndermez; özellikle yan etkili isteklerde test kodunu düzeltirken kullanılır.
  5. 401 ve 404 gövdeleri neden ayrı testler gerektirir?
    Cevabı göster
    JSONBulut'ta 404 gövdesi meta.status içerirken 401 gövdesi message içerir: hata sözleşmesi tutarsızdır.
