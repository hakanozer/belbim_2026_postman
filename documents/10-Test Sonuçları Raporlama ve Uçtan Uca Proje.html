10.1Proje kapsamı, iş senaryosu ve güvenlik sınırı

Bu konu nedir?

Final projesinde bir istemci, gönderi listesini alır; listeden bir kaydı seçip detayını ve yorumlarını okur. Bu zincir API'lerin birbirine bağlı kaynakları nasıl temsil ettiğini ve testte verinin nasıl taşındığını gösterir.

Neden önemlidir?

Üretim ekiplerinde liste → detay → ilişkili alt kaynak deseni katalog, sipariş, işlem ve kayıt API'lerinde yaygındır. Test, yalnızca 200 dönmesini değil; sonraki endpoint'in önceki yanıttan alınan kimliği kullandığını ve ilişkiyi koruduğunu doğrular.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • E-ticaretÜrün listesi → ürün detayı → yorumlar.
  • İçerik platformuYazı listesi → yazı → yorumlar.
  • Finans/operasyonİşlem listesi → işlem ayrıntısı → ilişkili olaylar; gerçek sistemde erişim kontrolü ayrıca gerekir.

Hangi durumlarda?

  • Bir kaynak başka endpoint'e kimlik verdiğinde.
  • Consumer contract/regresyon paketi hazırlanırken.
  • Endpoint refactor sonrası ilişki kopmasını yakalamak için.

10.2İstek 1: sayfalı Posts listesini okuma ve ID çıkarma

Bu konu nedir?

Liste endpoint'i meta bilgisi ve data kayıt dizisini döndürür. İlk script status'u, response shape'i ve kayıt ID'sinin kullanılabilir olduğunu doğrular; ardından ilk ID'yi collection variable'a yazar.

Neden önemlidir?

Sonraki isteklerde sabit ID kullanmak testi canlı verinin sırasına/kayda bağlı kılar. Yanıttan alınan değer zinciri gerçek koşuya göre uyarlarken testin hangi kaydı kullandığını görünür kılar.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • PaginationListe endpoint'i ve sayfa parametreleri.
  • Consumer contractYanıt zarfı ve ID alanı değişikliğini yakalama.

Hangi durumlarda?

  • Liste sonucundan detaya geçerken.
  • Collection Runner/CLI'da iterasyonlar arasında değişken taşırken.
Postman'da uygulama
  1. Folder içinde Posts - liste adlı GET request oluşturun.
  2. URL'yi {{baseUrl}}/api/posts yapın. Params alanına page=1 ve per_page=2 satırlarını ekleyin; gereksiz header eklemeyin.
  3. Scripts → Post-response alanına aşağıdaki kodu ekleyin.
  4. Send ile tek başına çalıştırın; Status, JSON Body, Test Results ve collection Variables içindeki postId değerini kontrol edin.
Kod örneği
JavaScriptPosts - liste / Scripts → Post-response
pm.test("Liste yanıtı 200 ve beklenen zarfı içerir", function () {
  pm.expect(pm.response.code).to.equal(200);
  const body = pm.response.json();
  pm.expect(body).to.be.an("object");
  pm.expect(body.data).to.be.an("array");
  pm.expect(body.meta).to.be.an("object");
});

const body = pm.response.json();
if (Array.isArray(body.data) && body.data.length > 0) {
  const firstId = body.data[0].id;
  pm.test("İlk kayıtta kullanılabilir id var", function () {
    pm.expect(firstId).to.exist;
  });
  pm.collectionVariables.set("postId", String(firstId));
} else {
  pm.collectionVariables.unset("postId");
  pm.test("Liste boş; zincir devam edemez", function () {
    pm.expect.fail("data boş; detay ve yorum istekleri için id yok.");
  });
  pm.execution.setNextRequest(null);
}
Kodun açıklaması
  • İlk pm.test status ve JSON şeklinin temel sözleşmesini kontrol eder; her satırın bütün alanlarını sabitlemez.
  • body.data[0].id canlı yanıttaki ilk kayıttan gelir; değer sabit değildir.
  • pm.collectionVariables.set değeri sonraki request'e taşır; String URL değişkeninde kullanılabilir biçime getirir.
  • Liste boşsa postId temizlenir, test başarısız olur ve Runner/CLI akışı durdurulur; eski bir koşudan kalmış ID yanlışlıkla kullanılmaz.

10.3İstek 2: detay endpoint'inde kimlik tutarlılığı

Bu konu nedir?

Detay request'i, liste yanıtında saklanan ID'yi path variable olarak kullanır. Test, status 200'ü ve dönen detay kaydının id değerinin istenen ID ile aynı olduğunu doğrular.

Neden önemlidir?

Yanlış ID'ye giden URL ya da cache/router karışıklığı, başarılı status koduyla yanlış kaydı döndürebilir. İlişki assertion'ı, testin doğru kaynağı kontrol ettiğini kanıtlar.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • REST kaynak API'leriListe → detay path parameter.
  • E-ticaret / içerikSeçilen ürün/yazı ile detail response eşleşmesi.

Hangi durumlarda?

  • Listeden detay açan uygulama akışında.
  • ID yönlendirmesi veya cache değişikliğinde.
Postman'da uygulama
  1. Posts - detay adlı GET request oluşturun ve URL'yi {{baseUrl}}/api/posts/{{postId}} yapın.
  2. Authorization = No Auth olduğunu doğrulayın; query veya body eklemeyin.
  3. Scripts → Pre-request içine koruyucu kodu, Post-response içine doğrulama kodunu ekleyin.
  4. Önce Posts - liste isteğini tek başına Send edin; collection postId değerini kontrol edin. Sonra detay isteğini Send edin.
  5. Test Results'ta 200 ve id eşleşme testlerini inceleyin.
Kod örneği
JavaScriptPosts - detay / Scripts → Pre-request
if (!pm.collectionVariables.get("postId")) {
  console.warn("postId yok; Posts - detay isteği atlanıyor.");
  pm.execution.skipRequest();
}
JavaScriptPosts - detay / Scripts → Post-response
pm.test("Detay yanıtı 200 ve seçilen id ile aynı", function () {
  pm.expect(pm.response.code).to.equal(200);
  const body = pm.response.json();
  pm.expect(body.data).to.be.an("object");
  pm.expect(String(body.data.id))
    .to.equal(pm.collectionVariables.get("postId"));
});
Kodun açıklaması
  • Pre-request guard, değişken boşsa eksik URL'li request göndermemek için pm.execution.skipRequest() çağırır; toplu koşuda etkili olur.
  • Post-response test gerçek response içindeki data.id'yi istenen postId ile string olarak karşılaştırır.
  • JSONBulut detail yanıtında data nesnesi bulunduğu gözlenmiştir; response schema veya API değişirse body alanını güncellemeden önce canlı yanıtı ve OpenAPI'yi doğrulayın.
Beklenen sonuç

Post id değeri listeden alınan postId ile aynıdır ve test geçer. Bu doğrulama, belirli post başlığına veya canlı içerik metnine bağımlı değildir.

10.4İstek 3: yorumların doğru posta bağlandığını doğrulama

Bu konu nedir?

Yorum endpoint'i aynı postId ile çağrılır ve her yorumdaki post_id değeri bu post ile aynı mı kontrol edilir. Yorum dizisinin boş olması tek başına başarısızlık nedeni değildir; her kayıt varsa ilişki tutarlı olmalıdır.

Neden önemlidir?

İlişkili kaynak endpoint'i yanlış parent ID'ye göre filtreliyorsa, response status 200 olsa da veri ilişkisi bozuk olabilir. Her öğeyi parent ID ile karşılaştırmak bu iş kuralını test eder.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Yorum / event alt kaynaklarıParent ID'ye bağlı kayıtları doğrulama.
  • Order line / transactionAlt kayıtların doğru parent'a ait oluşu.

Hangi durumlarda?

  • Parent-child endpoint'lerini test ederken.
  • Backend query/filter veya relation mapping değiştiğinde.
Postman'da uygulama
  1. Posts - yorumlar adlı GET request oluşturun; URL'yi {{baseUrl}}/api/posts/{{postId}}/comments yapın.
  2. Scripts → Pre-request'e aynı postId korumasını ekleyin.
  3. Scripts → Post-response alanına aşağıdaki ilişki doğrulamasını ekleyin.
  4. Liste, detay ve yorum isteklerini Collection Runner'da bu sırayla çalıştırın.
Kod örneği
JavaScriptPosts - yorumlar / Post-response
if (!pm.collectionVariables.get("postId")) {
  console.warn("postId yok; Posts - yorumlar isteği atlanıyor.");
  pm.execution.skipRequest();
}

pm.test("Yorum listesi 200 ve her yorum doğru post'a bağlı", function () {
  pm.expect(pm.response.code).to.equal(200);
  const body = pm.response.json();
  pm.expect(body.data).to.be.an("array");
  const expectedPostId = pm.collectionVariables.get("postId");
  body.data.forEach((comment, index) => {
    pm.expect(String(comment.post_id), "data[" + index + "].post_id")
      .to.equal(expectedPostId);
  });
});
Kodun açıklaması
  • Dizi boşsa forEach sıfır kez çalışır; bu test ilişkiyi ihlal eden bir yorum olmadığını söyler, yorum varlığını garanti etmez.
  • Her yorum için hata mesajına array index eklenir; başarısız satırı response içinde bulmak kolaylaşır.
  • Eğer API sayfalı yorum dönüyorsa yalnızca dönen sayfa kapsamındaki kayıtları doğruladığınızı rapor edin.
Beklenen sonuç
Gerçek API yanıtı (gözlendi)

29 Ekim 2026 tarihinde GET /api/posts/1/comments için 200 gözlenmiş ve dönen yorumların post_id değeri 1 olmuştur. Yorum adedi ve içerik zamanla değişebileceğinden test sayıyı sabitlemez.

Hata durumları ve çözümleri

10.5Collection Runner'da uçtan uca koşu ve hata analizi

Bu konu nedir?

Runner, folder içindeki liste → detay → yorum sırasını aynı koşuda yürütür. İlk request collection variable yazar; sonraki ikisi okur. Akışın tamamı her test sonucuyla birlikte rapora girer.

Neden önemlidir?

Tek tek Send ile yapılan manuel doğrulama, request sırası ve değişken state'ini kolayca atlar. Runner ile aynı senaryo baştan sona tekrarlanır ve bağımlılık hataları görünür olur.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • PR smokeSalt-okunur API sözleşme regresyonu.
  • Release öncesiSeçili endpoint zincirinin son kontrolü.
  • API değişikliğiİlgili folder'ı hedefleyerek hızlı doğrulama.

Hangi durumlarda?

  • Request'ler arasında veri taşındığında.
  • Aynı test paketinin tekrar çalışması gerektiğinde.
Postman'da uygulama
  1. 01 - Posts Zinciri folder'ını seçin ve Run collection/folder akışını açın; v12 görünümünde collection/folder menüsünden Run seçeneğini arayın.
  2. Environment olarak jsonbulut-test seçin; iteration data gerekmiyorsa dosya eklemeyin ve Iterations = 1 yapın.
  3. İstek sırasının liste → detay → yorumlar olduğunu ve sadece GET bulunduğunu kontrol edin.
  4. Run başlatın. Summary'de request/test counts ve failures; request ayrıntısında status, response time ve Test Results'ı inceleyin.
  5. Başarısızlıkta ilk kırılan halkadan başlayın: liste body/variable → detay id/path → yorum parent relation.
  6. İstek/yanıt, environment, saat, collection commit/sürümü ve hata mesajını hassas veri olmadan rapora kaydedin.
Beklenen sonuç

Üç request de 200 döner ve her test geçer. Sunucu/API değişikliği, ağ veya sözleşme farkı nedeniyle bu gözlem garanti değildir; beklenen-sonuç ile gerçekleşen sonucu ayrı kaydedin.

10.6CLI ile çalıştırma, rapor ve proje teslimi

Neden önemlidir?

Proje tesliminde testin başka bir bilgisayarda ve CI runner'da tekrarlanabilmesi gerekir. Collection, environment şablonu, bağımlılık sürümü ve rapor bu tekrarlanabilirliğin kanıtıdır.

Hangi alanlarda?

Hangi durumlarda?

  • Testi masaüstü dışında çalıştırmak gerektiğinde.
  • Sonucun sürüm kontrolü ve artifact olarak saklanması gerektiğinde.
Postman'da uygulama
  1. Collection'ı v2.1 JSON olarak collections/jsonbulut-regression.postman_collection.json adıyla export edin.
  2. Environment'ı environments/jsonbulut-test.postman_environment.json adıyla export edin; gerçek token/parola bulunmadığını kontrol edin.
  3. Ders 9'daki Postman CLI komutuyla login gerektirmeyen yerel koşu yapın. YAML --output raporu gerekiyorsa CLI'da API key ile login gerekeceğini hesaba katın; alternatif olarak Newman JSON rapor komutunu kullanın.

  5. Repository'ye collection, secret içermeyen environment/data, README veya takımın mevcut dokümantasyonunu ve CI workflow'unu teslim edin; run report'ını kontrollü artifact olarak saklayın.

10.7Bakım, kapsam değerlendirme ve ekip alıştırması

Bu konu nedir?

Test collection yaşayan bir üründür. API sözleşmesi, response shape, erişim davranışı ve veri hacmi değiştikçe testlerin amacı korunarak güncellenmesi gerekir.

Neden önemlidir?

Gereğinden katı test, zararsız alan eklemesinde kırılır; zayıf test ise kritik regresyonu kaçırır. Her assertion'ın hangi iş riskini kapsadığını açıklayabilmek sürdürülebilirliğin temelidir.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • API ownerSözleşme diff ve versioning.
  • QA leadRisk bazlı kapsam ve flaky test yönetimi.
  • SRE/ReleaseSLO, run artifact ve release gate.

Hangi durumlarda?

  • API alanı veya endpoint değiştiğinde.
  • Canlı incident sonrası regression eklerken.
  • Collection başka ekibe devredilirken.
Postman'da uygulama
  1. Her test için API requirement veya risk kaynağını kaydedin.
  2. Response'ta değişebilecek içerik, kayıt sayısı ve sabit ID gibi brittle beklentileri kaldırın; gerekli iş kuralını koruyun.
  3. API şeması değişince collection diff'ini review edin, testleri staging'de çalıştırın ve test verisinin etkisini onaylayın.
  4. Başarısız testte önce API davranışı mı, ortam mı, test kodu mu olduğunu sınıflandırın; düzeltme sonrası aynı koşuyu tekrarlayın.
  5. Takım alıştırması: liste request'inin per_page değerini 1 ve 2 ile iki ayrı izinli iterasyonda deneyin; response'ın data dizisi olduğunu doğrulayın, sabit kayıt içeriğine bağlanmayın.
Beklenen sonuç

Takım koleksiyonun neyi doğruladığını, neyi doğrulamadığını, hangi ortamda güvenle çalıştırılabileceğini ve başarısızlığın nasıl triage edileceğini açıklayabilir.

Bölüm özeti

  • Final akış üç gerçek OpenAPI GET endpoint'inden oluşur: Posts listesi → post detayı → yorumlar.
  • İlk gerçek id yanıttan alınır; collection variable ile diğer isteklere taşınır ve parent-child ilişkisi doğrulanır.
  • Testler yalnızca status kodunu değil; response shape, alan tipi ve gerçek ID ilişkisini kontrol eder.
  • Runner/CLI'da sıra ve environment doğrulanır; rapor başarısızlığın analizinde kanıt olarak kullanılır.
  • Sadece GET kullanılır; tanımda olmayan PATCH veya yan etkili çağrı uydurulmaz.

Sonraki bölüme hazırlık: Eğitim tamamlandı. Sonraki adım olarak collection'ı ekip review'ından geçirin, staging/CI'da onaylı salt-okunur koşu yapın ve test sahipliği ile API sözleşme güncelleme sürecini belirleyin.
