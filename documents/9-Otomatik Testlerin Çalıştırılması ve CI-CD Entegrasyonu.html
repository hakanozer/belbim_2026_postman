9Otomatik Çalıştırma ve CI/CD

Postman Desktop'ta doğruladığınız collection'ı önce Collection Runner'da, sonra komut satırında çalıştırın. Postman CLI ile Newman'ın farklılıklarını görün ve salt okunur JSONBulut testlerini bir CI iş akışına bağlayın.

  • Seviye: Orta–ileri
  • Süre: ~120 dk
  • Ön koşul: Ders 4, 6–8
  • Gerekli: export edilmiş collection
Önceki bölüm8. API Güvenlik ve Performans Kontrolleri
Sonraki bölüm10. Raporlama ve Uçtan Uca Proje

Bu bölümün öğrenme hedefleri

Collection Runner'da sıralı ve veri odaklı koşu yapmak.
Postman CLI 1.73.0 ve Newman 6.2.3 komutlarının kullanım alanlarını ayırmak.
Collection/environment/data dosyalarını tutarlı adlarla yönetmek.
CI'da test hatasını exit code ve raporla release kararına taşımak.
Araç ve sürüm notu

Sürüm doğrulaması: Bu içerikte kullanılan örnekler Postman CLI 1.73.0 ile kontrol edilmiştir. Newman örnekleri Newman 6.2.3 için hazırlanmıştır; komut satırındaki kurulu sürümü kendi ortamınızda postman --version ve newman --version ile teyit edin.

Postman CLI ve Newman aynı ürün değildir. Postman CLI, Postman'ın yerel collection-runner aracı ve güncel Postman ekosistemi özellikleriyle entegredir. Newman, Postman Collection v2.1 JSON'u komut satırında çalıştıran ayrı bir açık kaynak Node.js aracıdır. Bu derste JSONBulut'a yalnızca salt-okunur GET çağrıları gönderiyoruz.

9.1Collection Runner: istekleri sırayla çalıştırma

Bu konu nedir?

Collection Runner, collection veya seçili folder içindeki istekleri belirli sırayla tekrar çalıştırır; test script sonuçlarını, süreleri ve iterasyonları tek koşu görünümünde toplar.

Neden önemlidir?

Manuel Send tek bir isteğin anlık sonucunu gösterir. Runner ise regresyon paketinin aynı sırayla tekrarını sağlar ve ilk çağrıdan sonraki çağrılarda test davranışını karşılaştırır.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • QA regresyonuAynı kritik GET isteklerini release öncesi toplu çalıştırma.
  • API ekibiSözleşme değişikliği sonrası collection doğrulama.
  • Veri odaklı testCSV/JSON satırlarını iterasyon olarak kullanma.

Hangi durumlarda?

  • Birden fazla request aynı koşuda yürütülecekse.
  • İstekler arasındaki değişken bağımlılığını test etmek gerektiğinde.
Uygulamaya hazırlık

Önce GET /api/posts?page=1&per_page=2, GET /api/products/1 ve gerekirse GET /api/products/search?query=phone isteklerini test scriptleriyle collection'a kaydedin. Bu örnekler salt okunurdur; yan etkili POST/PUT/DELETE isteklerini Runner'a eklemeyin.

Postman'da uygulama
  1. Postman Desktop'ta çalışma alanını açın ve sol taraftaki Collections alanından çalıştıracağınız collection'ı seçin.
  2. Collection veya folder menüsünde Run / Run collection seçeneğini arayın. Postman v12 yardımındaki alternatif: collection'ı açıp Run görünümüne geçin; seçenek yerleşimi workspace görünümüne göre değişebilir.
  3. Run ekranında istek sırasını ve seçili request'leri kontrol edin; yanlışlıkla yan etkili çağrı olmadığını doğrulayın.
  4. Environment seçicisinden jsonbulut-test ortamını seçin. Iteration data kullanıyorsanız dosya yükleme alanına CSV/JSON ekleyin.
  5. Iterations ve request delay değerlerini ihtiyaca göre ayarlayın; salt-okunur örnekte bile aşırı tekrar ve gereksiz trafik oluşturmayın.
  6. Run düğmesiyle başlatın. Sonuçta passed/failed testleri, request sırasını, response time'ı ve iterasyonları inceleyin.

Postman 12.34.3: ne yapalım, ne yapmayalım?

Yapın
  • Koşu başlamadan önce collection, environment, request sırası ve URL hostunu doğrulayın.
  • Runner'daki başarısız request'i açıp status, response body ve Test Results'ı birlikte inceleyin.
Yapmayın
  • Production environment veya yan etkili istekleri onaysız toplu çalıştırmayın.
  • Runner'daki çoklu iterasyonu yük testi gibi değerlendirmeyin.
  • Sır/gerçek kullanıcı verisi içeren data file'ı dışa aktarmayın.
Beklenen sonuç

Runner özeti iterasyon sayısını, request sonuçlarını, assertion passed/failed sayısını ve süreleri gösterir. Bir testin yeşil olması yalnızca yazdığınız assertion'ların geçtiğini gösterir; test kapsamını otomatik olarak kanıtlamaz.

9.2Dosyaları dışa aktarma ve tutarlı proje yapısı

Bu konu nedir?

CLI/CI koşusu için collection, environment ve gerekiyorsa veri dosyası gerekir. Dosya adları, komutlardaki yollar ve repository yapısı birebir tutarlı olmalıdır.

Neden önemlidir?

Makinede çalışan testin CI'da bulunamaması çoğunlukla eksik export, yanlış yol, sır içeren environment veya farklı base URL kaynaklıdır.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Git tabanlı ekiplerReview edilebilir collection JSON ve test değişiklikleri.
  • CI/CDSabit isimli environment şablonu, ayrı gizli değişkenler ve rapor artifact'ı.

Hangi durumlarda?

  • Local'den CI'a geçerken.
  • Takımın collection'ı yeniden üretilebilir biçimde paylaşması gerektiğinde.
Uygulamaya hazırlık
MetinÖrnek repository ağacı
postman-api-tests/
├── collections/
│   └── jsonbulut-regression.postman_collection.json
├── environments/
│   └── jsonbulut-test.postman_environment.json
├── data/
│   └── posts-pages.csv
└── reports/
Postman'da uygulama
  1. Postman'da collection adının yanındaki menüyü açın, Export'u seçin; format olarak Collection v2.1 JSON'u seçip collections/jsonbulut-regression.postman_collection.json adıyla kaydedin.
  2. Environments alanından jsonbulut-test ortamını açın ve Export seçeneğini kullanarak environments/jsonbulut-test.postman_environment.json oluşturun.
  3. Environment export'tan önce apiToken, parola veya gerçek müşteri verisi bulunmadığını kontrol edin. Sırlar ayrı CI secret/store'dan sağlanmalıdır.
  4. CSV dosyasını data/posts-pages.csv adıyla data/ klasöründe saklayın. Dosya, sözdizimi ve encoding bakımından UTF-8 olmalıdır.
  5. Collection, environment şablonu ve veri dosyasını Git'te review edin; reports/ çalışma çıktıları ise genellikle .gitignore edilir.

9.3Postman CLI ile collection çalıştırma

Bu konu nedir?

Postman CLI, Postman collection'larını terminalden veya CI job'ından çalıştırır. Örnek burada yerel Collection JSON ve Environment JSON yollarını kullanır; Postman Cloud kaynağı kullanmak zorunlu değildir.

Neden önemlidir?

CLI, masaüstü etkileşimi olmadan testleri komut satırında çalıştırıp başarısızlıkta sıfır olmayan exit code döndürerek CI kapısına bağlanabilir. Güncel CLI akışı ve rapor seçenekleri Newman'dan farklıdır.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Geliştirici makinesiCommit öncesi aynı collection'ı hızlıca çalıştırma.
  • CI runnerPR/release adımında testi otomatik çalıştırma.

Hangi durumlarda?

  • Postman CLI yüklüyse ve CLI özellikleri/çalışma akışı tercih ediliyorsa.
  • Komut tabanlı test çalıştırma gerekiyorsa.
Uygulamaya hazırlık
Doğrulandı

Postman CLI 1.73.0'da yerel collection/environment ile koşu login olmadan çalışır. Login yokken CLI, bulut run ayrıntılarını yayımlamak için kimlik bilgisi olmadığını bildiren uyarı basabilir; yerel summary ve exit status yine de tamamlanabilir. --output YAML rapor dışa aktarımı ise Postman hesabıyla postman login gerektirir; bu koşul komutla doğrulanmıştır. CLI sürümleri ilerledikçe --help çıktısını ve kimlik doğrulama gereksinimini tekrar kontrol edin.

Kod örneği
TerminalPostman CLI — yerel, login gerektirmeyen koşu
postman --version
postman collection run \
  collections/jsonbulut-regression.postman_collection.json \
  --environment environments/jsonbulut-test.postman_environment.json
Kodun açıklaması
  • İlk komut kurulu CLI sürümünü gösterir.
  • collection run yerel collection JSON'unu çalıştırır; --environment ise aynı repodaki environment JSON'unu seçer.
  • Login olmadan terminal özeti ve test sonuçları alınır. --output istenirse Postman hesabıyla giriş gerekir; YAML raporu için aşağıdaki isteğe bağlı akışı kullanın.
  • Assertion/istek hatası non-zero exit status üretir; exit code'i baskılayan bayrakları quality gate amacıyla kullanmayın.
Kod örneği
Terminalİsteğe bağlı YAML raporu — CLI login gerekir
# POSTMAN_API_KEY değerini güvenli secret store'dan sağlayın.
postman login --with-api-key "$POSTMAN_API_KEY"
postman collection run \
  collections/jsonbulut-regression.postman_collection.json \
  --environment environments/jsonbulut-test.postman_environment.json \
  --output reports/postman-cli
Postman'da uygulama
  1. Terminal'i postman-api-tests/ repository kökünde açın.
  2. postman --version ile CLI'ı doğrulayın; kurulu değilse Postman'ın resmi Postman CLI kurulum yönergesini izleyin.
  3. Collection ve environment dosyalarının komutta yazıldığı adlarla mevcut olduğunu kontrol edin.
  4. Komutu çalıştırın; terminaldeki request/assertion sonuçlarını okuyun.
  5. reports/postman-cli/ altındaki YAML raporlarını inceleyin; test başarısızsa exit code ile CI job'ının kırmızı olduğunu doğrulayın.

Postman 12.34.3: ne yapalım, ne yapmayalım?

Yapın
  • Kullandığınız CLI'ın yerel --help çıktısını sürüm güncellemesi sonrası kontrol edin.
  • CI'da rapor klasörünü artifact olarak yükleyip retention/access politikasını uygulayın.
Yapmayın
  • Başarısız testleri --suppress-exit-code ile yeşil pipeline'a çevirmeyin.
  • --insecure ile TLS doğrulamasını kapatmayın.
  • CLI loglarını token veya kişisel veri içerebilecek şekilde açık paylaşmayın.
Beklenen sonuç

Başarılı koşuda CLI tamamlanır ve YAML raporu oluşur. Test hatasında terminal başarısızlığı görünür ve CI adımı non-zero exit status ile durur. Çıkış kodunu raporla birlikte okuyun; yalnızca komutun tamamlanması testlerin geçtiği anlamına gelmez.

9.4Newman ile collection çalıştırma

Bu konu nedir?

Newman, Postman Collection v2.1 dosyalarını Node.js üzerinde komut satırından çalıştıran ayrı bir açık kaynak araçtır. Postman CLI ile aynı değildir; seçenekleri, raporlama ve entegrasyon davranışı farklıdır.

Neden önemlidir?

Newman uzun süredir kullanılan, npm tabanlı ve CI sistemlerine kolay eklenen bir runner'dır. Ekip mevcut Newman pipeline'ı kullanıyorsa collection JSON'unu yeniden yazarak başlaması gerekmez.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Mevcut npm tabanlı CINewman'ın halihazırda kullanılan pipeline'a eklenmesi.
  • Yerel otomasyonNode.js toolchain'i olan geliştirici makinesi.

Hangi durumlarda?

  • Newman'ın sürümünü sabitleyip collection JSON çalıştırmak istediğinizde.
  • Postman CLI'a özgü özelliklere ihtiyaç yoksa ve mevcut ekosistem Newman ise.
Uygulamaya hazırlık
Bilgi

Newman için Node.js ve npm gerekir. Newman 6.2.3 örneği proje bağımlılığı olarak sabitlenebilir; takımın Node.js destek politikasını izleyin. npm install --save-dev newman@6.2.3 komutunu proje kökünde çalıştırın ve package-lock.json dosyasını commit edin.

Kod örneği
TerminalNewman — CSV iterasyonlu run
npx newman --version
npx newman run \
  collections/jsonbulut-regression.postman_collection.json \
  --environment environments/jsonbulut-test.postman_environment.json \
  --iteration-data data/posts-pages.csv \
  --reporters cli,json \
  --reporter-json-export reports/newman-report.json
Kodun açıklaması
  • npx newman run yerel collection dosyasını çalıştırır.
  • --environment ortam dosyasını, --iteration-data CSV satırlarını her biri bir iterasyon olacak şekilde kullanır.
  • --reporters cli,json terminal özeti ve JSON reporter'ını etkinleştirir; --reporter-json-export JSON çıktısının yoludur.
  • Newman collection formatı/CLI seçenekleri için sabitlenen sürümde npx newman run --help kontrol edin.
Postman'da uygulama
  1. Node.js/npm sürümünü doğrulayın ve proje kökünde npm install --save-dev newman@6.2.3 komutunu çalıştırın.
  2. Package manifest ve lockfile'ı repository'de saklayın; CI'da npm ci kullanın.
  3. Collection, environment ve CSV dosyalarının yollarını kontrol edin; environment içine gerçek sır koymayın.
  4. Komutu çalıştırın. reports/ klasörünü önceden oluşturun; Newman JSON raporu burada yazılır.
  5. Terminalde iterations, requests, tests, failures özetini; JSON raporunda request/assertion ayrıntısını inceleyin.

9.5GitHub Actions üzerinde CI örneği

Bu konu nedir?

CI (sürekli entegrasyon), değişiklik Git'e gönderildiğinde testleri otomatik çalıştırır. API test adımı başarısızsa pipeline kırmızı kalır ve release kararı görünür olur.

Neden önemlidir?

Aynı collection'ı geliştirici makinesinden bağımsız, temiz bir runner'da tekrar çalıştırmak ortam farkı ve unutulan manuel testi azaltır. CI bir güvenlik sınırıdır; üretim verisine erişim otomatik olarak verilmemelidir.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Pull requestSalt-okunur contract/smoke testlerini merge öncesi çalıştırma.
  • NightlyDaha kapsamlı, izinli ve test ortamında planlı regresyon.
  • ReleaseYayın öncesi onaylı test paketi.

Hangi durumlarda?

  • API collection değiştiğinde.
  • Release için tekrarlanabilir test gate'i gerektiğinde.
Uygulamaya hazırlık

Aşağıdaki workflow, Newman bağımlılığını lockfile ile kurar ve JSONBulut'un herkese açık salt-okunur test collection'ını çalıştırır. API_TOKEN satırı yalnızca kendi API'niz Bearer token istiyorsa örnektir; JSONBulut'taki seçili GET'ler için token gerekmez.

Kod örneği
YAML`.github/workflows/api-tests.yml`
name: API regression

on:
  pull_request:
  push:
    branches: [main]

jobs:
  postman-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: mkdir -p reports
      - name: Run read-only API collection
        run: >-
          npx newman run collections/jsonbulut-regression.postman_collection.json
          --environment environments/jsonbulut-test.postman_environment.json
          --iteration-data data/posts-pages.csv
          --reporters cli,json
          --reporter-json-export reports/newman-report.json
      - name: Upload run report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: api-test-report
          path: reports/newman-report.json
          if-no-files-found: warn
Kodun açıklaması
  • Workflow dosyasını repository kökünde .github/workflows/api-tests.yml adıyla kaydedin.
  • npm ci lockfile'da sabitlenen bağımlılıkları kurar; lockfile yoksa önce geliştirici ortamında oluşturup commit edin.
  • if: always() rapor yükleme adımını test adımı başarısız olsa bile çalıştırır; test adımı yine de pipeline'ı başarısız kılar.
  • Rapor dosyası oluşmadan job başlarsa reports/ dizinini hazırlayan bir adım ekleyin: mkdir -p reports.
  • Sır gereken kendi servisinizde GitHub repository/environment secret oluşturun; secret'ı environment JSON'a veya YAML'a yazmayın. Sadece izinli endpoint'e aktarın.
Kod örneği
YAMLYalnızca kendi servisi için secret aktarımı
- name: Add an authorized secret for your own service
  env:
    SERVICE_TOKEN: ${{ secrets.SERVICE_TOKEN }}
  run: >-
    npx newman run collections/my-service.postman_collection.json
    --environment environments/staging.postman_environment.json
    --env-var "apiToken=$SERVICE_TOKEN"
    --reporters cli,json
    --reporter-json-export reports/service-report.json
Postman'da uygulama

Postman 12.34.3: ne yapalım, ne yapmayalım?

Yapın
  • GitHub Secret/Environment Secret kullanın; PR kaynağına göre fork policy ve secret erişimini gözden geçirin.
  • Pipeline çıktısında sırları maskeleyin; rapor artifact erişimi/retention süresini belirleyin.
Yapmayın
  • Secret'ı collection, environment export, YAML, CLI argüman logu veya commit'e koymayın.
  • Fork kaynaklı güvenilmeyen PR'a üretim secret'ı açmayın.
  • continue-on-error ile test başarısızlığını quality gate'ten saklamayın.
Beklenen sonuç

Pull request veya main push'ta Newman adımı çalışır. Test geçerse job yeşil; assertion ya da request başarısızsa Newman non-zero code ile job kırmızı olur. Rapor artifact'ı, hata analizine yardımcı olur; ham response hassas veri içermemelidir.

  • Newman 6.2.3, Node.js/npm ile ayrı bir collection runner'dır; örneği npx newman run biçimindedir.
