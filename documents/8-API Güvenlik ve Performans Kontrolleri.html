Yetki sınırı: yalnızca size ait veya yazılı olarak test etme izni verilen sistemlerde çalışın. Bu derste brute-force, kimlik tahmini, tarama, enjeksiyon payload'ı veya yoğun istek üretimi yoktur.

Bu ders yalnızca token'sız profil isteği gibi düşük etkili erişim kontrolü örneklerini kullanır. Başarılı token edinmeye veya başkasına ait hesaba erişmeye çalışmayın.

8.1Güvenlik testinin kapsamı ve güvenli çalışma biçimi

Bu konu nedir?

API güvenlik testi, yalnızca servisin yanıt verip vermediğine değil; kimlerin hangi veriye, hangi koşulda erişebildiğine bakar. Bir Postman isteğiyle tüm güvenlik doğrulanmaz; bu derste temel, düşük etkili kontrolleri öğreneceğiz.

Neden önemlidir?

Kurumsal projelerde kimlik doğrulama hatası müşteri verisini açığa çıkarabilir; hassas alanların log veya yanıtta görünmesi de veri koruma ihlaline yol açabilir. Erken ve küçük kontroller, kod incelemesi ve güvenlik testlerini tamamlamaz; onları destekler.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Finans ve sigortaKimlik, hesap ve poliçe uçlarının erişim kuralları.
  • SağlıkHasta verisine rol ve amaç sınırıyla erişim.
  • E-ticaretSipariş ve müşteri verisinin yalnızca yetkili oturumda görünmesi.
  • Kurumsal platformServisler arası token kapsamı ve hata yanıtlarında veri sızıntısı.

Hangi durumlarda?

  • Yeni endpoint veya rol eklendiğinde.
  • Kimlik doğrulama/yetkilendirme middleware'i değiştiğinde.
  • Güvenlik bulgusu kapatıldıktan sonra regresyon kontrolünde.
Postman'da uygulama
  1. İş emrinde API hostu, ortam, hesap/rol ve izin verilen test saat aralığını yazılı olarak teyit edin.
  2. Test ortamını seçin; üretimde test yapmanız ayrıca açıkça onaylanmadıkça üretim seçmeyin.
  3. Gerçek müşteri verisi yerine sentetik veri kullanın; yetkisiz veya yoğun çağrıları kapsam dışı bırakın.
  4. İstek adı, tarih-saat, environment, durum kodu ve test sonucu ile kanıtı kaydedin.

Postman 12.34.3: ne yapalım, ne yapmayalım?

Yapın
  • Yalnızca onaylı host, hesap, rol ve düşük etkili senaryolarla çalışın.
  • Test hesabı ve sentetik veri kullanın; istek sıklığını ekip sınırlarına göre tutun.
  • Güvenlik bulgularını kanıt, etki ve tekrar üretim koşullarıyla kapalı kanaldan raporlayın.
Yapmayın
  • Gerçek kullanıcı ID'lerini tahmin ederek başka kişilerin kayıtlarını sorgulamayın.
  • Parola denemesi, token brute-force, üretim taraması veya yüksek hacimli istek göndermeyin.
  • Token, parola veya kişisel veriyi ekran görüntüsü, Console veya rapora kopyalamayın.
Beklenen sonuç
Durdurma kuralı

Bir isteği göndermeye yetkiniz olduğundan emin değilseniz göndermeyin. Önce API sahibi ve güvenlik sorumlusundan kapsamı yazılı alın.

8.2Kimlik doğrulama ve yetkilendirme kontrolleri

Bu konu nedir?

Kimlik doğrulama (authentication) “kimsin?”, yetkilendirme (authorization) “bu kaynağa erişebilir misin?” sorusudur. Geçersiz/eksik kimlik bilgisinin uygun şekilde reddedilmesi gerekir; rol bazlı erişim ise ayrı bir test hesabı ve açık test izni gerektirir.

Neden önemlidir?

401 genellikle geçerli kimlik doğrulama bilgisinin bulunmadığını/geçersiz olduğunu; 403 ise kimliği bilinen istemcinin bu işleme yetkili olmadığını ifade eder. Gerçek uygulama sözleşmesini kontrol edin; her API bu ayrımı aynı biçimde uygulamayabilir.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • JSONBulutOpenAPI bearerAuth şeması, global değil; belirli operasyonlara uygulanmıştır.
  • Kurumsal servisRol/kapsam matrisi, test hesabı ve staging ortamı gerekir.

Hangi durumlarda?

  • Endpoint güvenlik tanımı değiştiğinde.
  • 401/403 davranışını regresyon testine alırken.
Uygulamaya hazırlık

Aşağıdaki istek, JSONBulut'un GET /api/profile/me korumalı operasyonunu token olmadan çağırır. Şemada bu endpoint Bearer auth gerektirir; 29 Ekim 2026 tarihli gözlemde token'sız yanıt 401 olmuştur. Sunucu yanıtı değişebilir; testiniz gözlemi değil, sözleşmede beklenen erişim reddini kontrol eder.

Postman'da uygulama
  1. Postman'da izinli JSONBulut workspace'inde yeni HTTP request açın; adı SEC - Profile token yok olsun.
  2. Method GET, URL {{baseUrl}}/api/profile/me yapın. Authorization sekmesini açıp Type olarak No Auth seçin; Headers içine token veya kişisel bilgi eklemeyin.
  3. Scripts → Post-response alanına aşağıdaki kodu ekleyin.
  4. İsteği yalnızca izinli kullanım kapsamında Send edin. Status ve Test Results alanlarını inceleyin.
Kod örneği
JavaScriptPost-response — izinli 401 kontrolü
pm.test("Korumalı profil token olmadan reddedilir", function () {
  pm.expect(pm.response.code).to.equal(401);
});

pm.test("401 yanıtı JSON hata nesnesidir", function () {
  pm.expect(pm.response.headers.get("Content-Type") || "")
    .to.include("application/json");
  const body = pm.response.json();
  pm.expect(body).to.be.an("object");
  pm.expect(body.message).to.be.a("string");
});
Kodun açıklaması
  • pm.response.code durum kodunu okur; burada sözleşmede korumalı uç için tanımlanan 401'i bekliyoruz.
  • Yanıt Content-Type değerinde JSON olduğunu kontrol eder ve message alanının tipini doğrular; hata metninin içeriğini sabitlemez.
  • Bu test başarısız olursa token ekleyerek testi “yeşile boyamayın”; önce kullanılan host, auth ayarı, API sözleşmesi ve gerçek yanıtı inceleyin.
Beklenen sonuç
Gerçek API yanıtı (gözlendi)

Token'sız canlı istekte 401 gözlenmiştir. Sözleşme/test ortamı farklı davranırsa gerçek durum kodunu ve gövdeyi kaydedip API sahibiyle doğrulayın; eğitimdeki gözlem, geleceğe dönük garanti değildir.

Hata durumları ve çözümleri

8.3Hata yanıtı ve hassas veri sızıntısı kontrolü

Bu konu nedir?

Hata yanıtı istemciye sorunu açıklamalı, ancak parola, token, gizli anahtar veya stack trace gibi sırları açığa çıkarmamalıdır. Testte yalnızca hassas alan adlarının varlığını arayacağız; kişisel veriyi yazdırmayacağız.

Neden önemlidir?

Detaylı hata gövdeleri log toplama sistemlerine veya destek kayıtlarına kopyalanabilir. Bir sırın tek yanıtta görünmesi bile olay müdahalesi gerektirebilir; bulunan bulguyu güvenli kanaldan derhal bildirin.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Kimlik servisleriLogin ve token yenileme hata yanıtları.
  • Ödeme / müşteri API'leriHata gövdesinde kart/kimlik/iletişim bilgisinin bulunmaması.
  • GatewayStack trace, iç host ve yapılandırma ayrıntılarının dışarı sızmaması.

Hangi durumlarda?

  • API hata şeması veya exception handler değiştiğinde.
  • Güvenlik düzeltmesi sonrası regresyonda.
Uygulamaya hazırlık
Dikkat

Bu tarama örneği yanıtı değiştirmez. JSONBulut'un herkese açık salt okunur endpoint'inde de özel kullanıcı verisi bulunacağını varsaymayın; gerçek hassas veriyle test etmeyin.

Kod örneği
JavaScriptPost-response — hassas alan adlarını tarama
function findSensitiveKeys(value, path, found) {
  if (Array.isArray(value)) {
    value.forEach((item, index) => findSensitiveKeys(item, path + "[" + index + "]", found));
  } else if (value && typeof value === "object") {
    Object.keys(value).forEach((key) => {
      if (/(password|access_token|refresh_token|secret|authorization)/i.test(key)) {
        found.push(path ? path + "." + key : key);
      }
      findSensitiveKeys(value[key], path ? path + "." + key : key, found);
    });
  }
}

pm.test("Yanıtta açık sır alanı yok", function () {
  const contentType = pm.response.headers.get("Content-Type") || "";
  if (!contentType.includes("application/json")) {
    pm.expect.fail("JSON dışı yanıt; önce içerik türünü inceleyin.");
  }
  const found = [];
  findSensitiveKeys(pm.response.json(), "", found);
  pm.expect(found, "Hassas anahtar yolları: " + found.join(", ")).to.be.empty;
});
Kodun açıklaması
  • Yardımcı fonksiyon nesne/dizi içinde özyinelemeli dolaşır; yalnızca hassas anahtar adlarını rapora ekler, değerleri yazdırmaz.
  • Anahtar listesi örnek amaçlıdır. Kurumunuzun veri sınıflandırmasına göre security/privacy ekibiyle güncelleyin.
  • Bir eşleşme bulunduğunda sır değerini paylaşmayın; isteği durdurun ve onaylı olay bildirim sürecini kullanın.
Beklenen sonuç

Güvenli, herkese açık yanıt için test geçer. Hassas anahtar adı görünürse test kırmızı olur ve yalnızca anahtar yolunu gösterir. Eşleşme tek başına güvenlik açığı kanıtı değildir; alanın içeriği ve sözleşmedeki sınıflandırma yetkili ekipçe değerlendirilir.

8.4Girdi doğrulama: canlı API ile güvenli sınır

Bu konu nedir?

Girdi doğrulama, API'nin eksik, biçimsiz veya sınır dışı girdiye ne yaptığını kontrol eder. Negatif testlerde, veri oluşturma/değiştirme ihtimali varsa gerçek ortamda gelişigüzel payload gönderilmez.

Neden önemlidir?

Hatalı girdi beklenmedik 500, veri bozulması veya bilgi sızıntısı doğurabilir. Kurumsal ekip, negatif girdileri sözleşme ve iş kuralı üzerinden seçer; üretim dışı test verisini temizleme planı hazırlar.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Form ve arama API'leriBoş, fazla uzun veya izin verilmeyen alanlar.
  • Finansal işlemlerTutar ve para birimi sınırları.
  • Profil / kayıt API'leriŞema, zorunlu alan ve erişim kontrolü.

Hangi durumlarda?

  • OpenAPI şeması veya validasyon kuralı değiştiğinde.
  • Sınır değerleri regresyona eklerken.
Uygulamaya hazırlık
Güvenlik Sınırı

JSONBulut'ta GET /api/posts?per_page=0 isteği 500 / Division by zero döndürdüğü 29 Ekim 2026 gözlemi vardır. Bu hatalı girdiyi gerçek serviste tekrar tekrar denemeyin. Bu ders için salt-okunur uçta yalnızca kabul edilen normal değerleri kullanın; 0/negatif/çok büyük değer senaryolarını mock veya yazılı izinli test ortamında çalıştırın.

Postman'da uygulama
  1. API sözleşmesindeki required, format, minimum/maximum kurallarını çıkarın.
  2. Her kurala bir geçerli değer, hemen alt/üst sınır ve eksik değer senaryosu tasarlayın.
  3. Test ortamında yan etkisiz bir mock ya da izole kayıt kullanın; cleanup adımını önceden tanımlayın.
  4. Yanıt kodu, hata şeması, veri değişmediği ve hassas bilgi bulunmadığını doğrulayın.

Postman 12.34.3: ne yapalım, ne yapmayalım?

Yapın
  • per_page=1 gibi sözleşme içinde normal ve düşük etkili değerlerle liste sorgusu yapın.
  • Negatif senaryonun beklenen sonucunu API sahibiyle onaylayın.
Yapmayın
  • Canlı ortamda bilinen 500 üreten per_page=0 isteğini eğitim uğruna çalıştırmayın.
  • POST/PUT/DELETE isteğini gerçek veride deneme amacıyla göndermeyin.
  • API'nin tanımadığı query/body alanlarını destekleniyor gibi raporlamayın.
Beklenen sonuç

Canlı JSONBulut için bu bölümde yalnızca düşük etkili, geçerli GET örneği çalıştırılır. Sınır ve hatalı girdiler test planında belgelenir, ancak yazılı onay ve izole ortam olmadan gönderilmez.

8.5Tekil yanıt süresini ölçme ve eşik belirleme

Bu konu nedir?

Postman, tek isteğin yaklaşık yanıt süresini pm.response.responseTime üzerinden görmenizi sağlar. Bu ölçüm, istemci tarafından gözlenen tek çağrı süresidir; istatistiksel performans veya yük testi değildir.

Neden önemlidir?

Bir API değişikliğinin yanıtı belirgin yavaşlatıp yavaşlatmadığını smoke/regresyon koşusunda erken fark edebilirsiniz. Ancak CI makinesi, ağ, DNS, servis yükü ve soğuk başlangıç ölçümü etkiler.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Sürüm smoke testiBir kritik okuma endpoint'i beklenen temel aralığın içinde mi?
  • Servis seviyesi izlemeSLO/SLA ekipçe tanımlanmışsa tekil ölçüm yardımcı sinyaldir.

Hangi durumlarda?

  • Tek bir endpoint'in hızlı regresyon kontrolünde.
  • Eşik yalnızca servis sahibi ve ölçüm ortamı tarafından belirlendiğinde.
Uygulamaya hazırlık

Eşik örneği 1500 ms, yalnızca gösterim için temsili başlangıç değeridir; JSONBulut için SLA değildir. Önce aynı test ortamında art arda, düşük frekanslı ölçüm alın; dağılımı ve CI gürültüsünü dikkate alıp ekipçe eşik belirleyin.

Kod örneği
JavaScriptPost-response — tekil süre kontrolü
const responseTimeMs = pm.response.responseTime;
const thresholdMs = 1500; // Örnek eşik; servis SLO'su değildir.

pm.test("Yanıt süresi örnek eşiğin altında", function () {
  pm.expect(responseTimeMs).to.be.a("number");
  pm.expect(responseTimeMs).to.be.below(thresholdMs);
});
Kodun açıklaması
  • pm.response.responseTime milisaniye cinsinden ölçümü verir.
  • thresholdMs burada eğitim için örnektir; kurumsal SLO ve ölçüm koşullarıyla değiştirilmelidir.
  • Tek istek sonucu dalgalanabilir; tek başarısız örnekle kapasite sorunu ilan etmeyin. Aynı ortamda örnekleri toplayıp trendi inceleyin.
Postman'da uygulama
  1. Kaydettiğiniz salt-okunur GET /api/posts?page=1&per_page=2 isteğini açın.
  2. Scripts → Post-response içine kodu ekleyin ve isteği birkaç kez, aralarda makul bekleme bırakarak çalıştırın.
  3. Her çalıştırmada response time ve Test Results değerlerini kaydedin; Postman Console'da gereksiz yük oluşturmayın.
  4. Gerçek performans ihtiyacı için k6/JMeter/Gatling gibi yük testi aracını, onaylı test ortamında ve kapasite planıyla kullanın.
Beklenen sonuç
Dikkat

Postman'da tekil istek ölçümü eşik kontrolüdür. Eşzamanlı sanal kullanıcı, ramp-up, throughput veya stres profili üretmez; kapsamlı yük/stres testi yerine geçmez.

8.6Sonuçların kanıtlanması ve raporlama

Bu konu nedir?

Bir güvenlik veya performans bulgusu, yalnızca “test kırmızı oldu” demek değildir. Yeniden üretim adımı, ortam, endpoint, rol, zaman, beklenen/gerçekleşen sonuç ve etki birlikte raporlanır.

Neden önemlidir?

Geliştirici ekibin sorunu tekrar üretmesi ve düzeltmenin doğrulanması gerekir. Kanıtı en aza indirin: gerçek sırları, token'ları ve kişisel veri değerlerini rapora almayın.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • QA / AppSecTriage ve düzeltme iş kaydı.
  • Servis ekibiSözleşme veya middleware düzeltme doğrulaması.
  • Release yönetimiRisk, kapsam ve karar kaydı.

Hangi durumlarda?

  • Test başarısız olduğunda.
  • Düzeltme sonrası regresyon yapılırken.
  • SLO ihlali eğilimi fark edildiğinde.
Postman'da uygulama
  1. Postman yanıtında Status, Headers, Body ve Test Results'ı birlikte inceleyin; gerektiğinde Console'u açın.
  2. İstek adı, collection sürümü/commit'i, environment adı, tarih-saat, test edilen host ve yalnızca gerekli kanıtı yazın.
  3. Güvenlik bulgusunu onaylı kapalı kanal üzerinden ilgili ekip ve önem derecesiyle iletin.
  4. Düzeltmeden sonra aynı kontrollü test koşullarını tekrarlayın; sonucu eski bulguya bağlayın.
Beklenen sonuç

Rapor, başka bir mühendisin aynı izinli ortamda testi güvenle tekrar edebilmesine yetecek bilgiyi içerir; gizli değerleri içermez.

Bölüm özeti

  • Yetkisiz erişim ve güvenlik kontrolleri yalnızca yazılı izinli kapsamda yapılır; bu içerik saldırı testi talimatı değildir.
  • JSONBulut'ta korumalı profil endpoint'i Bearer auth ister; token'sız 401 canlı gözlemi zamana bağlıdır.
  • Hassas veri testi anahtar adlarını kontrol eder ve sır değerlerini yazdırmaz.
  • Hatalı/sınır girdilerini canlı sistemde değil, izole ve onaylı test ortamında deneyin.
  • pm.response.responseTime tekil süre ölçer; yük/stres testi değildir.

Sonraki bölüme hazırlık: Ders 9'da aynı salt-okunur kontrolleri Collection Runner, Postman CLI ve Newman ile toplu/otomatik çalıştıracağız. Hazırlık: izinli GET isteklerinizi collection'a kaydedin.

Bölüm sonu uygulaması

SEC - Profile token yok isteğini No Auth ile çalıştırıp 401 testini doğrulayın; API yanıtı değişirse gözlemi kayda alın.

Kendi izinli mock yanıtınızda access_token anahtarı ekleyip hassas alan tarama testinin yalnızca anahtar yolunu raporladığını gösterin.

Kendi test ortamınız için tekil yanıt süresi eşiği önerin; neden bunun yük testi olmadığını iki cümlede açıklayın.

Bulgu şablonu hazırlayın: kapsam, endpoint, environment, zaman, beklenen/gerçekleşen, etki, hassas veri içermeyen kanıt.

    401 kimlik doğrulama yok/geçersiz; 403 ise doğrulanmış istemcinin yetkisi yok anlamına gelir, ancak API sözleşmesini kontrol etmek gerekir.
  2. JSONBulut'taki her endpoint token ister mi?
    Cevabı göster
    Hayır. OpenAPI'de global security yok; Bearer auth yalnızca ilgili operasyonlarda tanımlıdır.
  3. pm.response.responseTime < 1500 testi yük testi midir?
    Cevabı göster
    Hayır; tekil istek süresini kontrol eder.
  4. Hassas alan eşleştiğinde neden değerini loglamıyoruz?
    Cevabı göster
    Sır/veri sızıntısının kapsamını büyütmemek ve raporda gizli bilgiyi tekrar ifşa etmemek için.
  5. per_page=0 gözlemi bu eğitimde canlı olarak tekrar edilmeli mi?
    Cevabı göster
    Hayır; daha önce 500 ürettiği gözlenmiştir. Yalnızca izole, yazılı izinli test ortamında ele alınmalıdır.
