5.1Kimlik doğrulama ve yetkilendirme: iki ayrı soru

Bu konu nedir?

Kimlik doğrulama (authentication) “sen kimsin?” sorusunu yanıtlar; yetkilendirme (authorization) “bu işlemi yapabilir misin?” sorusunu yanıtlar. Birincisi geçilse bile ikincisi reddedebilir.

DurumKodAnlamıTest beklentisi
Kimlik yok / geçersiz / süresi dolmuş401 UnauthorizedKimlik doğrulanamadı.Yanıt 401; gövdede içsel ayrıntı yok
Kimlik geçerli, izin yok403 ForbiddenKimlik biliniyor, işlem yasak.Yanıt 403 (ya da kaynağı gizlemek için 404)
Kimlik geçerli, yetkili200 / 2xxİşlem tamamlandı.Beklenen veri; yalnızca yetkili alanlar
Neden önemlidir?

API güvenliği ihlallerinin büyük kısmı, uygulama içinde değil yetkilendirme eksikliğinde yaşanır (örn. bir kullanıcı başkasının kaydına kimlik numarasını değiştirerek ulaşır — BOLA/IDOR). Bu yüzden yetkisiz erişim senaryoları, fonksiyonel testin parçasıdır.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Bankacılık / ödemeHesap, kart ve işlem uçları katı kimlik ve yetki denetimine tabidir; denetim her sürümde bu testleri ister.
  • Sigorta / sağlıkMüşteri A'nın poliçe/dosya verisini müşteri B'nin görememesi KVKK ve mevzuat gereğidir.
  • B2B / partner API'leriHer partnerin yalnızca kendi verisini görmesi, anahtar/token bazlı yetkiyle sağlanır.
  • Yönetim panelleriRol bazlı yetki (admin / operatör) testleri, ayrıcalık yükseltme açıklarını yakalar.

Hangi durumlarda?

  • Yeni bir korumalı endpoint eklendiğinde.
  • Rol/izin modeli değiştiğinde.
  • Güvenlik denetimi/pentest öncesi hazırlıkta.
  • Token süre ve yenileme davranışı değiştiğinde.

5.2Yöntemler: API Key, Basic, Bearer, JWT ve OAuth 2.0 (genel eğitim)

Bu konu nedir?
Önemli ayrım

Bu konudaki yöntemler genel API bilgisidir. **JSONBulut'un OpenAPI tanımı yalnızca bearerAuth (HTTP bearer, JWT) güvenlik şemasını içerir**; API Key, Basic Auth, OAuth 2.0 JSONBulut'ta tanımlı değildir ve orada çalışıyormuş gibi gösterilmeyecektir. Uygulamaları güvenli bir çalışma tahtasında (Postman Echo) yapacağız.

Neden önemlidir?

Yanlış yöntemi test etmek ya da yöntemin güvenlik özelliklerini bilmemek, yanlış güvenlik varsayımlarına yol açar. Örneğin “Basic Auth şifreli” sanısı, TLS olmadan parolanın düz metin gibi taşınmasına yol açar; “JWT payload'u gizli” sanısı da sızıntıdır.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Entegrasyon projeleriKarşı tarafın hangi yöntemi istediği ilk toplantıda öğrenilir; yanlış yöntem haftalarca entegrasyon gecikmesidir.
  • Mikroservis / SSO ortamlarıOAuth 2.0 + JWT kombinasyonu en yaygın kurulumdur; test ekibi token almayı da otomasyona dahil eder.

Hangi durumlarda?

  • Yeni bir API'ye bağlanırken.
  • Güvenlik mimarisi incelemesinde.
  • Token alma adımını CI'ya taşırken.

5.3Authorization sekmesi uygulaması (Postman Echo laboratuvarı)

Bu konu nedir?

Postman'da Authorization sekmesi, seçtiğiniz Auth type'a göre doğru header'ı veya parametreyi sizin için üretir. Bu konuda üç yöntemi, kimlik bilgisi gerektirmeyen ve herkese açık Postman Echo servisinde deneyeceğiz; böylece JSONBulut'a gerçek token göndermeden mekanik oturur.

Neden önemlidir?

Elle yazılmış Authorization header'ları (yanlış boşluk, eksik Bearer) en sık yapılan kimlik hatasıdır. Auth sekmesi biçimi garanti eder, değişken kullanımını teşvik eder ve collection düzeyinde tek yerden yönetilmesini sağlar.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Kimlik doğrulamalı tüm servislerCollection düzeyinde bir kez tanımlanan auth, yüzlerce isteğe miras kalır; token değişince tek noktadan güncellenir.
  • Çoklu ortam (test/staging)Her ortamın kendi token değeri environment değişkeninden gelir; request metni değişmez.

Hangi durumlarda?

  • Korumalı bir API ile ilk kez çalışırken.
  • Auth türü değiştiğinde (Basic → Bearer).
  • Token'ı koddan değil değişkenden besleme alışkanlığı kazanırken.
Uygulamaya hazırlık
  • Yapay değerler (gerçek değil): demoToken = DEMO-TOKEN-NOT-REAL, demoApiKey = DEMO-KEY-NOT-REAL.
  • Postman Echo'nun belgelenmiş herkese açık demo Basic Auth bilgisi: kullanıcı postman, parola password; bunlar gizli değildir ve yalnızca postman-echo.com/basic-auth için geçerlidir.
  • Değişkenler: demoToken, demoApiKey, demoUser, demoPass — bunları Ders 6'daki gibi bir environment'a ekleyeceksiniz; şimdilik request'te doğrudan yazabilirsiniz.
Postman'da uygulama
  1. Yeni bir HTTP isteği açın: metot GET, adres https://postman-echo.com/headers.
  2. Authorization sekmesine tıklayın. Auth type açılır listesinden Bearer Token seçin.
  3. Token alanına {{demoToken}} yazın. (Değişken henüz tanımlı değilse alan kırmızı/uyarılı görünür; değeri doğrudan DEMO-TOKEN-NOT-REAL olarak da girebilirsiniz.)
  4. Headers sekmesinde hidden başlıkları açın: Authorization satırını Postman'ın eklediğini görün; bu satırı elle değiştirmeyin.
  5. Send'e tıklayın. Echo yanıtında headers.authorization değerinin Bearer DEMO-TOKEN-NOT-REAL olduğunu görün.
  6. İsteği çoğaltın: Auth type → API Key seçin; Key alanına X-Api-Key, Value alanına DEMO-KEY-NOT-REAL yazın, Add to olarak Header seçin. Gönderin: yanıtta headers["x-api-key"] görünür.
  7. Üçüncü bir istek: GET https://postman-echo.com/basic-auth; Auth type → Basic Auth; Username postman, Password password. Gönderin: yanıt {"authenticated": true} olmalı. Parolayı bilerek yanlış yazıp tekrar gönderin: 401 görürsünüz.

Postman 12.34.3: ne yapalım, ne yapmayalım?

Yapın
  • Kimlik bilgisini Authorization sekmesinde girin; mümkünse {{değişken}} kullanın.
  • Collection düzeyinde bir kez ayarlayıp isteklerde Inherit auth from parent (Inherited) seçeneğini kullanın.
Yapmayın
  • Authorization sekmesi ve Headers sekmesine aynı kimlik bilgisini ikisine birden yazmayın: Postman'ın ürettiği auth header'ı Headers sekmesinde ezemezsiniz.
  • Gerçek token'ı Echo gibi üçüncü taraf servislere göndermeyin; üçüncü taraf bunu loglayabilir.
  • Token'ı Params/URL (query) içine koymayın; URL'ler loglanır.
Kod örneği
JavaScriptPost-response — Bearer Token denemesi
// 1) Bearer — GET https://postman-echo.com/headers  (Auth type: Bearer Token, Token: {{demoToken}})
pm.test("Authorization header'ı Bearer biçiminde gönderildi", function () {
  const echoed = pm.response.json().headers.authorization;
  pm.expect(echoed).to.equal("Bearer " + pm.variables.get("demoToken"));
});
JavaScriptPost-response — API Key denemesi
// 2) API Key — GET https://postman-echo.com/headers  (Auth type: API Key, Key: X-Api-Key, Add to: Header)
pm.test("API anahtarı header olarak gönderildi", function () {
  const headers = pm.response.json().headers;
  pm.expect(headers["x-api-key"]).to.equal(pm.variables.get("demoApiKey"));
});
JavaScriptPost-response — Basic Auth denemesi
// 3) Basic — GET https://postman-echo.com/basic-auth  (Auth type: Basic Auth)
pm.test("Basic kimlik doğrulaması başarılı", function () {
  pm.expect(pm.response.code).to.equal(200);
  pm.expect(pm.response.json().authenticated).to.be.true;
});
Kodun açıklaması
  • Echo, aldığı header'ları geri yansıtır: gönderdiğiniz kimlik başlığının tam biçimini görürsünüz.
  • Bearer testi, değeri koda gömmez; pm.variables.get("demoToken") ile aynı değişkenden okur: değer değişince test de bozulmaz.
  • Header adları yanıtta küçük harfle gelir (x-api-key): HTTP header adları büyük/küçük harfe duyarsızdır.
Beklenen sonuç

Üç denemede de durum kodu 200, yanıtta sırasıyla authorization, x-api-key ve authenticated: true değerleri. Yanlış Basic parolasında 401.

5.4JSONBulut'un gerçek yetkilendirme modeli: Bearer JWT

Bu konu nedir?

OpenAPI tanımı tek bir güvenlik şeması içerir: bearerAuth (HTTP, bearer, biçim JWT). Global güvenlik yoktur; yalnızca aşağıdaki 10 operasyon üzerinde operasyon düzeyinde tanımlıdır:

OperasyonBearer?Sözleşmedeki yanıt kodlarıGözlem (token'sız GET, 29 Ekim 2026)
POST /api/auth/loginHayır200, 401Çalıştırılmadı (veri oluşturmaz ama kimlik bilgisi ister)
POST /api/auth/signupHayır201, 422Çalıştırılmadı (kullanıcı oluşturur)
POST /api/auth/refreshEvet200Çalıştırılmadı
POST /api/auth/logoutEvet200, 401Çalıştırılmadı
GET /api/profile/meEvet200, 401401 {"message":"Token is Invalid!"}

GET /api/users/{id}/postsEvetyalnızca 200 tanımlı401 (sözleşmede tanımsız!)

POST/PUT/DELETE /api/users…Evet200, 401Çalıştırılmadı (veri değiştirir)
Gerçek API yanıtı (gözlendi)

Aynı GET /api/profile/me isteği, Authorization: Bearer INVALID-TOKEN-FOR-TRAINING (yapay değer) ile gönderildiğinde yanıt yine 401 olur, ama gövde farklıdır: {"message":"Token not Parsed!"}. Yani sunucu “token yok” ile “token biçimsiz”i farklı mesajlarla ayırır; sözleşme bu mesajları tanımlamaz.

Neden önemlidir?

Test beklentisini gözlenen davranışa değil sözleşmeye bağlamak için hangi uç koruma gerektiriyor bilmek gerekir. Yukarıdaki tablo, kapsam planının (hangi uçlar yetkisiz test edilecek) ve eksik sözleşme maddelerinin (users alt uçlarında 401 tanımsız) kaynağıdır.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Kimlik doğrulamalı her servisHangi uçların korumalı olduğunun envanteri güvenlik testinin ilk adımıdır; unutulan korumasız uç tipik bir güvenlik bulgusudur.
  • API sözleşmesi yönetimiSözleşmede tanımsız ama gözlenen davranış (401), sözleşme güncelleme talebi olarak API sahibine iletilir.

Hangi durumlarda?

  • Yeni sürümde korumalı/korumasız uç listesini gözden geçirirken.
  • Yetkisiz erişim testi planı yazarken.
  • OpenAPI sözleşme kalitesi değerlendirilirken.
Token alma akışı (yalnızca yetkili hesap)
Sözleşme içinde çelişki olabilir

Giriş ve token yanıt biçimi doğrulanmadı. OpenAPI login yanıtı için data adlı bir nesne tanımlar; ancak örnek değer (access_token, token_type, expires_in: "3600") data zarfı olmadan yazılmıştır. Gerçek yanıt hangi biçimde olduğunu, yalnızca yetkili bir hesapla kendi çağrınızda göreceksiniz. Aşağıdaki script iki biçimi de karşılar (savunmacı kodlama).

Uygulamaya hazırlık
  • Eğitmeninizden/API sahibinden yazılı onayla bir test hesabı alın (e-posta + parola). Hesabı kendiniz oluşturmak için POST /api/auth/signup kullanmak veri oluşturur; ancak eğitmen onayı ve yapay veriyle (örn. egitim.ogrenci01@example.com, parola yöneticisiyle üretilmiş geçici bir parola) yapılmalıdır.
  • Bilgileri Secure environment değişkenlerine yazın: testUserEmail, testUserPassword (Konu 5.7).
  • Hesap yoksa bu konuyu sadece okuyun; token gerektiren istekleri çalıştırmayın.
Postman'da uygulama
  1. Yeni istek: POST {{baseUrl}}/api/auth/login.
  2. Authorization sekmesinde No Auth seçin (login ucu Bearer istemez).
  3. Body → raw → JSON seçin ve gövdeye { "email": "{{testUserEmail}}", "password": "{{testUserPassword}}" } yazın (değişkenler Secure environment'tan gelir; gerçek değerleri istek metnine yazmayın).
  4. Scripts → Post-response sekmesine aşağıdaki kodu yapıştırın.
  5. Send — yalnızca onaylı test ortamında ve hesapta. Başarılıysa Console'da “Token kaydedildi” mesajını ve environment'ta accessToken değişkenini görürsünüz.
  6. Korumalı bir isteğin (GET {{baseUrl}}/api/profile/me) Authorization sekmesinde Bearer Token seçip Token alanına {{accessToken}} yazın.
Kod örneği
JavaScriptLogin isteği — Post-response (kavramsal: gerçek hesap gerekir)
// POST {{baseUrl}}/api/auth/login → Scripts → Post-response
// Yalnızca YETKİLİ test hesabıyla ve onaylı ortamda çalıştırın.
const body = pm.response.json();
const tokenInfo = body && body.data ? body.data : body;   // sözleşme örneği zarflı/zarfsız olabilir

pm.test("Login 200 döndü ve access_token var", function () {
  pm.expect(pm.response.code).to.equal(200);
  pm.expect(tokenInfo, "token nesnesi").to.have.property("access_token");
});

if (tokenInfo && tokenInfo.access_token) {
  pm.environment.set("accessToken", tokenInfo.access_token);
  const lifetimeSeconds = Number(tokenInfo.expires_in || 3600);
  pm.environment.set("tokenExpiresAt", String(Date.now() + lifetimeSeconds * 1000));
  console.log("Token kaydedildi (değer gizli). Süre (sn):", lifetimeSeconds);
}
Kodun açıklaması
  • body && body.data ? body.data : body — yanıt data zarfıyla gelirse onu, gelmezse gövdenin kendisini kullanır.
  • pm.environment.set("accessToken", ...) — token'ı environment değişkenine yazar; değişkeni Secure işaretleyin.
  • expires_in metin olarak geldiği için Number(...) ile sayıya çevirdik; tokenExpiresAt, bitiş zamanını milisaniye cinsinden tutar.
  • Token'ın kendisini console.log ile yazdırmadık: Console çıktıları ekran görüntülerine ve loglara sızar.
Beklenen sonuç

Başarılı login'de 200 ve accessToken, tokenExpiresAt environment değişkenleri. Bu akışı JSONBulut üzerinde biz çalıştırmadık; yanıt biçimi hesabı olan eğitmen/öğrenci tarafından doğrulanmalıdır.

5.5Token yaşam döngüsü: süre, yenileme ve çıkış

Bu konu nedir?

Token geçici bir kimlik kartıdır: bir süre sonra geçersiz olur. Üç davranış bilinmelidir: süre dolması (401), yenileme (refresh) (OpenAPI'de POST /api/auth/refresh, Bearer ister) ve çıkış (logout) (POST /api/auth/logout, Bearer ister).

Neden önemlidir?

Uzun koşan test paketleri (gece regresyonu, soak testleri) token süresini aşar; süresi dolan token yüzünden testlerin yarısı “401” ile kırmızı olur, oysa sorun servis değil test altyapısıdır. Otomasyon bu durumu önceden tespit etmeli ya da token'ı yenilemelidir.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Uzun koşan regresyon paketleriBinlerce istek birkaç saat sürebilir; token süresi kısa ise ara ara yenileme gerekir.
  • Mobil / SPA istemcileriSüre dolduğunda otomatik refresh akışı, kullanıcı deneyimini belirleyen davranıştır.
  • Güvenlik testleriÇıkıştan sonra eski token'ın geçersiz olması (token revocation) önemli bir kontroldür.

Hangi durumlarda?

  • Gece/CI koşularında token ömrünü aşan paketlerde.
  • Refresh/logout davranışı değiştiğinde.
  • Süresi dolmuş token ile 401 beklentisi test edilirken.
Kod örneği
JavaScriptCollection → Pre-request — token süre denetimi
// COLLECTION → Scripts → Pre-request
// Token süresini denetler; gereksiz 401 hatalarının nedenini önceden gösterir.
const token = pm.environment.get("accessToken");
const expiresAt = Number(pm.environment.get("tokenExpiresAt") || 0);
const safetyMs = 60 * 1000;   // bitişten 1 dakika önce uyar

if (!token) {
  console.warn("accessToken yok: korumalı isteklerde 401 beklenir. Önce login isteğini çalıştırın.");
} else if (Date.now() + safetyMs >= expiresAt) {
  console.warn("Token süresi dolmak üzere/doldu. Refresh veya yeniden login yapın.");
}
JavaScriptPost-response — JWT payload çözme (sahte token)
// JWT payload çözme — bir token'ın exp alanını okumak için YARDIMCI kod.
// Aşağıdaki token SAHTE bir eğitim örneğidir (imza geçersiz, gizli veri yok).
function base64UrlEncode(obj) {
  return btoa(JSON.stringify(obj)).replace(/=+$/, "").replace(/\+/g, "-").replace(/\//g, "_");
}

function decodeJwtPayload(token) {
  const part = token.split(".")[1];
  const base64 = part.replace(/-/g, "+").replace(/_/g, "/");
  const padded = base64 + "=".repeat((4 - (base64.length % 4)) % 4);
  return JSON.parse(atob(padded));
}

const fakeToken = [
  base64UrlEncode({ alg: "HS256", typ: "JWT" }),
  base64UrlEncode({ sub: "demo-user", role: "training", exp: 4102444800 }),
  "EGITIM-IMZASI-GERCEK-DEGIL"
].join(".");

pm.test("JWT payload çözülebiliyor", function () {
  const payload = decodeJwtPayload(fakeToken);
  pm.expect(payload.sub).to.equal("demo-user");
  pm.expect(payload.exp).to.be.a("number");
});

pm.test("exp alanı gelecekte (yapay token)", function () {
  const payload = decodeJwtPayload(fakeToken);
  pm.expect(payload.exp * 1000).to.be.above(Date.now());
});
Kodun açıklaması
  • Date.now() + safetyMs >= expiresAt — süre bitmeden bir dakika önce uyarı üretir.
  • console.warn — test sonucu üretmez; Console'da uyarı satırı olarak görünür. İsterseniz buraya pm.execution.skipRequest() ya da login isteğini zincirleme çağıran bir akış koyabilirsiniz (Ders 7).
  • JWT çözme: base64url → base64 dönüşümü, eksik = dolgusu ve atob/JSON.parse. Bu imzayı doğrulamaz; yalnızca payload'u okur.
  • Gerçek token'ı kendi test hesabınızla çözdüğünüzde de çıktıyı Console'a tamamen yazdırmayın (role, sub gibi alanlar hassastır).
Beklenen sonuç

Sahte token testlerinin ikisi de geçer. Token guard kodu accessToken tanımlı değilse Console'da sarı uyarı yazar; hiçbir test üretmez.

5.6Yetkisiz erişim testleri: otomatik ve güvenli

Bu konu nedir?

Yetkisiz erişim testi, korumalı bir ucu kimlik olmadan (ya da bozuk kimlikle) çağırıp reddedildiğini ve yanıtın veri sızdırmadığını doğrular. Bu bölümde, token gönderilmeyen salt okunur GET isteklerini otomatikleştiriyoruz.

Neden önemlidir?

Yetkisiz erişim testi, yeni eklenen bir ucun yanlışlıkla korumasız bırakılmasını yakalayan en ucuz regresyon testidir. Hata ortaya çıkarsa etkisi kritiktir (veri sızıntısı).

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Her kimlik doğrulamalı servisHer yeni endpoint için bir 401 testi, güvenlik kontrol listesinin standart maddesidir.
  • Penetrasyon testi öncesiTest ekibi, korumasız uç bulgularını pentest'ten önce kapatır.

Hangi durumlarda?

  • Yeni endpoint eklendiğinde.
  • Ağ geçidi/yetkilendirme katmanı değiştiğinde.
  • Kimlik sağlayıcı değişikliğinde.
Uygulamaya hazırlık
  • Yalnızca izinli test ortamı: https://jsonbulut.com. Bu isteklerde token yok; veri değişmez.
  • İstekler (Authorization: No Auth): GET {{baseUrl}}/api/profile/me, GET {{baseUrl}}/api/users?page=1&per_page=1, GET {{baseUrl}}/api/users/1.
  • Bozuk token isteği: aynı profile/me isteği, Bearer Token = INVALID-TOKEN-FOR-TRAINING.
Kod örneği
JavaScriptPost-response — yetkisiz erişim testi
// Token GÖNDERİLMEYEN korumalı uçlar için → Scripts → Post-response
pm.test("Token olmadan korumalı uç 401 döner", function () {
  pm.expect(pm.response.code).to.equal(401);
});

pm.test("Hata gövdesi mesaj içeriyor ve içsel ayrıntı sızdırmıyor", function () {
  const text = pm.response.text();
  pm.expect(text).to.be.a("string").that.is.not.empty;
  pm.expect(text.toLowerCase()).to.not.match(/stack|exception|trace|sql|\/var\/|\.php/);
});

pm.test("Yanıtta kullanıcı verisi yok", function () {
  const body = pm.response.json();
  pm.expect(body).to.not.have.property("data");
});
Kodun açıklaması
  • pm.response.text() — gövdeyi ham metin olarak okur; hata metninde yığın izi ipuçlarını (stack, sql, dosya yolu) arıyoruz.
  • to.not.match(/…/) — düzenli ifade eşleşmemeli. Mesajın kendisini birebir assert etmedik: sözleşmede yok.
  • Aynı kod bozuk token isteğinde de çalışır; çünkü beklenti aynıdır (401, sızıntı yok).
Postman'da uygulama
  1. Üç isteği oluşturup 04-Guvenlik-Yetkisiz klasörüne kaydedin.
  2. Her birinde Authorization sekmesinin No Auth olduğunu ve Headers'ta Authorization olmadığını doğrulayın.
  3. Kodu Scripts → Post-response'a yapıştırıp her isteği gönderin.
  4. Bozuk token isteğini ekleyin: Auth type → Bearer Token, Token INVALID-TOKEN-FOR-TRAINING; aynı testlerle gönderin.

Postman 12.34.3: ne yapalım, ne yapmayalım?

Yapın
  • Yetkisiz testleri kendi klasöründe tutun; sonradan CI'da ayrı çalıştırılabilsin.
  • Bozuk token olarak açıkça yapay bir değer kullanın.
Yapmayın
  • Aynı korumalı uca art arda çok sayıda deneme göndermeyin (rate-limit/kilitleme riski).
  • Başka bir kullanıcıya ait gerçek bir token'ı “yetkisiz” test için kullanmayın.
  • Yetkisiz erişim denemelerini yazılı izniniz olmayan sistemlerde yapmayın.
Beklenen sonuç

Üç kimliksiz istek ve bozuk token isteği için üç test de geçer: 401, gövde yalnızca message içerir. Gözlem: {"message":"Token is Invalid!"} (token yok) ve {"message":"Token not Parsed!"} (bozuk token).

Sonuç nasıl doğrulanır?

Başarıyı yalnızca “401 geldi” değil, gövdede sızıntı olmaması da kanıtlar. 200 dönen bir korumalı uç, testi kırmızıya çevirmeli ve kritik bulgu olarak raporlanmalıdır.

5.7Hassas bilgilerin güvenli yönetimi: Secure değişken, Vault ve dokümantasyonda maskeleme

Bu konu nedir?

Token, parola ve API anahtarı sır (secret)tir. Postman'da sırları saklamanın üç katmanı vardır: Secure işaretli değişken, Postman Vault (local/shared) ve CI'da ortam sırları. Dokümantasyonda ve ekran görüntülerinde ise değerler maskelenir.

Neden önemlidir?

Sızan bir token, süre dolana kadar sahibinin yetkisiyle her işlemi yapabilir. Kurumlarda Postman collection'larının e-postayla/Git ile paylaşılması en sık görülen sızıntı yoludur: dışa aktarılan JSON içinde sırlar kalır.

Sahada nerede ve ne zaman ihtiyaç duyulur?

Hangi alanlarda?

  • Regülasyona tabi kurumlarGizli bilgi sızıntısı doğrudan uyum ihlalidir; denetimde Postman çıktıları da incelenir.
  • Ortak Git depolarıDışa aktarılmış collection/environment dosyaları depoya girerse sır geçmişte kalıcı olur.

Hangi durumlarda?

  • Her token/parola kullanımında.
  • Collection/environment dışa aktarmadan önce.
  • Ekran görüntüsü, kayıt, eğitim materyali hazırlarken.
Postman'da uygulama
  1. Kenar çubuğunda Items → Environments'ı açın ve environment'ınızı seçin.
  2. accessToken değişkeninin yanında kilit simgesine (Secure) tıklayın.
  3. Bir istekte değişkenin değeri hâlâ görünüyorsa Authorization alanındaki Sensitive value uyarısının üzerine gelip Set as Variable ile değeri bir değişkene taşıyın.
  4. Sırları Postman Vault'ta tutmak isterseniz, Vault'u açıp bir secret ekleyin ve istekte {{vault:secret-adı}} biçiminde başvurun konum doğrulanmadı Vault'un arayüzdeki giriş noktası ve plan kullanılabilirliği
  5. Değişkenin yanındaki Share simgesine sırlar için tıklamayın.

Postman 12.34.3: ne yapalım, ne yapmayalım?

Yapın
  • Sırları yalnızca local value'da tutun ya da Vault'a koyun.
  • Dışa aktarma öncesi environment'ı ve collection'ı sır açısından inceleyin.
Yapmayın
  • Token/parolayı shared value'ya, request Body/URL'sine, Description'a veya collection script'ine yazmayın.
  • Sırların bulunduğu environment'ı Git'e commit etmeyin.
  • Token'ı tamamen Console'a yazdırmayın.
Kod örneği
JavaScriptMaskeleme yardımcı fonksiyonu
// Sırları loga yazarken maskeleyin — token'ın kendisini asla yazdırmayın.
function maskSecret(value) {
  if (typeof value !== "string" || value.length === 0) return "(boş)";
  if (value.length <= 8) return "****";
  return value.slice(0, 4) + "…" + value.slice(-2) + " (uzunluk " + value.length + ")";
}

console.log("Token:", maskSecret(pm.environment.get("accessToken")));
console.log("Örnek maske:", maskSecret("ORNEK-SAHTE-DEGER-1234567890"));
Kodun açıklaması
  • Kısa değerler tamamen **** olur; uzun değerlerde yalnızca ilk 4 ve son 2 karakter ile uzunluk gösterilir.
  • Dokümantasyonda ve ekran görüntülerinde gerçek bir değer yerine her zaman <TOKEN> ya da **** yer tutucusu kullanın; bu eğitimdeki tüm örnekler yapay değerlerle yazılmıştır.

Bölüm özeti

  • Kimlik doğrulama = “kimsin?”, yetkilendirme = “yapabilir misin?”; 401 ve 403 ayrı sorunlardır.
  • API Key, Basic, Bearer, JWT ve OAuth 2.0 genel yöntemlerdir; **JSONBulut yalnızca bearerAuth (JWT) tanımlar** ve yalnızca 10 operasyonda kullanır.
  • Gerçek gözlem: korumalı GET'ler token'sız 401 {"message":"Token is Invalid!"}, bozuk token ile 401 {"message":"Token not Parsed!"} döner.
  • Authorization sekmesinde Auth type seçilir; header'ı Postman üretir, Headers sekmesinde ezilmez. Collection düzeyinde bir kez ayarlanıp Inherit edilir.
  • Sırlar: Secure değişken, Vault, local value; asla Body/URL/Description/Console/commit.

    Cevabı göster
